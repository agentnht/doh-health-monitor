# Концепция: Geosite DNS routing и режимы работы DoH

**Дата фиксации обсуждения:** 2026-11-19  
**Статус:** архитектурное обсуждение; это не утверждённое ТЗ реализации и не разрешение на изменение кода.  
**Базовая точка для будущей реализации:** ветка \`main\`, версия 2.2.1.

## 1. Цель обсуждения

Рассматривается отказ от Auto Hosts как отдельного динамического списка доменов и перенос определения Geosite-попаданий на сторону LucX-UI/Xray — туда, где уже находятся правила маршрутизации.

Предполагаемое разделение ответственности:

- **LucX-UI/Xray** определяет по своим правилам, к какой DNS-ветке направить запрос.
- **Плагин** проверяет доступность настроенных DoH-серверов, выбирает активный DoH и обслуживает направленный к нему DNS-поток согласно выбранному режиму.
- **Quad9 или другой настроенный fallback** используется для обычного разрешения имён в тех случаях, которые определит выбранный режим и его конфигурация.

Основная цель — не дублировать внутри плагина список Geosite, если панель/Xray уже умеет определять соответствующие домены.

## 2. Как пришли к этой идее

В ходе обсуждения PR #10 возник вопрос: зачем нужен Auto Hosts, если Geosite уже содержит классификацию доменов?

Рассматривался вариант:

1. Панель/Xray сопоставляет домен с Geosite-правилами.
2. DNS-запрос, который попал под нужное правило, направляется на DNS listener плагина.
3. Плагин возвращает IP активного DoH endpoint.
4. Запрос, который не попал под правило, направляется в Quad9 либо иной явно настроенный fallback.

При таком подходе плагину не требуется динамически добавлять QNAME в Auto Hosts, хранить пользовательские домены, обновлять LastSeen/ExpiresAt и удалять устаревшие записи. Само правило попадания в нужную DNS-ветку определяется панелью/Xray.

Важное техническое условие: один общий DNS listener не получает от Xray отдельный признак «какое правило совпало». Поэтому панель/Xray должны действительно разделить потоки до передачи запроса плагину — например, направлять их в разные DNS upstream/listener или обеспечить иным проверенным способом. Нельзя считать, что сам DNS-пакет содержит информацию о сработавшем routing rule.

## 3. Два взаимоисключающих режима плагина

Плагин работает строго в одном из двух режимов. Режим задаётся конфигурацией; одновременно применять оба способа формирования DNS-ответа нельзя. **Режим 1 является значением по умолчанию.**

### Режим 1. Возврат IP активного DoH endpoint

Xray определяет домены, которые должны направляться в DNS listener плагина, используя Geosite. Для запросов, попавших в этот поток:

1. Плагин использует отдельный список DoH endpoint-ов, предназначенный только для этого режима.
2. Плагин проверяет доступность endpoint-ов и выбирает один активный по алгоритму проверок, описанному в разделе 5.
3. Для DoH URL вида `https://dns.server.com/dns-query` плагин через bootstrap разрешает hostname `dns.server.com` и получает IP-адреса endpoint-а. Например, если bootstrap-разрешение вернуло `12.12.12.12`, именно этот IP endpoint-а возвращается клиенту в DNS-ответе.
4. Если hostname endpoint-а разрешается в несколько IP-адресов, необходимо сохранить и использовать существующую поддержку нескольких адресов в коде. Для A/AAAA применяются адреса соответствующего семейства согласно логике DNS-ответа.
5. Плагин возвращает клиенту IP выбранного активного DoH endpoint-а. Он **не выполняет обычное разрешение имени запрошенного сайта**.

Важно различать три вида адресов: IP DoH endpoint-а, полученный bootstrap-разрешением его hostname; IP bootstrap DNS resolver-а; IP запрошенного клиентом сайта. В ответе режима 1 используется первый. IP bootstrap resolver-а и IP сайта не подменяют IP endpoint-а.

### Режим 2. Разрешение реального имени сайта

Xray также определяет по Geosite, какие домены направлять в плагин. Для полученного запроса плагин выполняет обычное разрешение запрошенного доменного имени и возвращает реальный IP этого домена.

DNS-выход режима 2 настраивается отдельно:

- По умолчанию используется системный resolver операционной системы сервера, на котором работает плагин.
- В качестве альтернативы пользователь может выбрать DNS-сервер из отдельного редактируемого списка. Список должен поддерживать обычные DNS-серверы и DoH-серверы.
- Этот список DNS-выходов режима 2 независим от списка DoH endpoint-ов режима 1. Изменение одного списка не должно менять или переопределять другой.

Системный resolver означает resolver ОС самого сервера/окружения плагина, а не автоматически DNS-подсистему Xray. При реализации необходимо исключить DNS-петлю, например если системная конфигурация указывает обратно на listener плагина.

### Взаимоисключение и общие правила

- В конфигурации активен только один режим; режим 1 — значение по умолчанию.
- Xray/панель отвечает за Geosite-сопоставление и направление DNS-запроса в нужный поток. Плагин не определяет Geosite-категорию запроса.
- Списки endpoint-ов режима 1 и DNS-выходов режима 2 раздельные.
- Режим 1 возвращает адрес DoH endpoint-а, полученный bootstrap-разрешением hostname этого endpoint-а; режим 2 возвращает адрес запрошенного домена.
- Переключение режима должно менять именно способ формирования DNS-ответа, не смешивая синтетический endpoint IP с обычным разрешением имени.

Предварительные имена параметров (не утверждённая схема config.json):

- `dns_mode: endpoint_ip` — режим 1, значение по умолчанию.
- `dns_mode: resolver` — режим 2.

## 4. Fallback и поведение при ошибках

### 4.1. Согласованная матрица fallback

Fallback двух режимов не пересекается: ошибка в одном режиме не должна незаметно переключать запрос на другой режим или на другой тип DNS-разрешения.

| Ситуация | Режим 1 — IP активного DoH endpoint-а | Режим 2 — разрешение имени сайта |
|---|---|---|
| Активный DoH не выбран | `blackhole`; не переходить к обычному resolver | Не относится к этому режиму |
| Bootstrap не смог получить IP hostname endpoint-а | Кандидат не пригоден; selector может выбрать другой здоровый DoH из списка режима 1. Если активного кандидата нет — `blackhole` | Для DoH-upstream bootstrap разрешает только hostname самого upstream, а не QNAME клиента |
| Доступен только IPv4 или только IPv6 | Вернуть адреса имеющегося семейства; не требовать одновременного наличия обоих семейств | Не относится к формированию ответа режима 1 |
| Для запрошенного семейства адреса нет, но другое семейство есть | Для A вернуть только IPv4; для AAAA — только IPv6. Если адреса запрошенного семейства нет — NODATA, не подменять тип RR | Не относится к формированию ответа режима 1 |
| Нет ни IPv4, ни IPv6 endpoint-а | `blackhole` | Не относится к этому режиму |
| Сетевая ошибка/таймаут при проверке endpoint-а или bootstrap | Не использовать обычный resolver. Исключить непригодного кандидата; если selector не выбрал другой здоровый DoH — `blackhole` | Перейти к следующему upstream режима 2 |
| DNS-ошибка при проверке endpoint-а | Не использовать обычный resolver. Кандидат считается непригодным; если другого активного DoH нет — `blackhole` | Для upstream-level ошибок (например, SERVFAIL/REFUSED или непригодный/обрезанный ответ) перейти к следующему upstream |
| Все upstream режима 2 исчерпаны | Не относится к этому режиму | `blackhole`; не переключаться на режим 1 |
| Валидный NXDOMAIN или NODATA для запрошенного имени | Не относится к этому режиму | Вернуть валидный DNS-ответ; это результат разрешения имени, а не отказ самого upstream |
| QNAME не попал под Geosite-правило | Запрос не должен направляться в поток режима 1 | Запрос обрабатывается отдельным DNS-путём, определённым Xray/панелью |

`blackhole` в этой матрице означает отсутствие fallback к обычному разрешению исходного домена и отсутствие успешного ответа с подменённым адресом. Конкретное wire-представление отказа (например, DNS SERVFAIL/REFUSED либо действие на стороне Xray) должно быть проверено в интеграционной схеме до реализации.

В режиме 1 ActiveDoHSelector по-прежнему может переключиться на другой здоровый endpoint из собственного списка. Это штатный выбор активного DoH, а не fallback на DNS-resolver: исходное имя сайта всё равно не разрешается.

В режиме 2 список upstream-ов независим от списка endpoint-ов режима 1. По умолчанию первым используется системный resolver ОС сервера, где работает плагин; дополнительные обычные DNS- и DoH-upstream-ы проверяются далее в настроенном порядке. Транспортная ошибка, таймаут, непригодный ответ или upstream-level DNS-ошибка приводит к попытке следующего upstream. NXDOMAIN и NODATA являются валидными ответами и сами по себе не должны запускать fallback.

Если все upstream режима 2 исчерпаны без пригодного ответа, запрос завершается по политике `blackhole`. Не следует возвращать случайный успешный результат или переходить к режиму 1.

### 4.2. Bootstrap — отдельная функция, не fallback QNAME

Bootstrap используется для разрешения hostname самого DoH endpoint-а, чтобы плагин мог установить соединение с endpoint по IP, сохранив исходный hostname для TLS SNI и HTTP Host.

Bootstrap не предназначен для разрешения обычного QNAME клиента и не заменяет список upstream-ов режима 2. Для DoH-upstream режима 2 bootstrap нужен только на этапе получения адреса его hostname. Список bootstrap-resolver-ов и список DNS-upstream-ов режима 2 — разные роли и не должны смешиваться в конфигурации.

Особенно важно не допустить петлю: системный resolver ОС режима 2 не должен в итоге отправлять запросы обратно на DNS listener этого же плагина. При обнаружении такой конфигурации её нужно отклонять либо явно запрещать запуск соответствующего пути до отдельного безопасного решения.

### 4.3. TTL и кэширование

**Режим 1:**

- TTL синтетического A/AAAA ответа не должен превышать оставшееся время актуальности выбранного endpoint IP (freshness/validity ActiveDoHSelector).
- Дополнительно TTL может ограничиваться общим верхним пределом кэша. Нельзя продлевать жизнь endpoint IP за счёт TTL кэша.
- Если endpoint IP устарел или выбор активного DoH изменился, старый ответ больше не должен выдаваться из кэша.
- Все адреса одного endpoint-набора получают согласованную TTL-политику. Для A возвращаются только IPv4, для AAAA — только IPv6.

**Режим 2:**

- Сохранять TTL, полученный от upstream, и уменьшать его при выдаче из кэша.
- Время жизни кэшированной записи ограничивать минимальным TTL записей ответа и настроенным MaxTTL.
- MinTTL не должен искусственно увеличивать TTL: если upstream TTL меньше настроенного минимума, такой ответ не кэшировать.
- Для NXDOMAIN и NODATA использовать отрицательный TTL из SOA: min(SOA RR TTL, SOA.MINIMUM), согласно RFC 2308. Если пригодного SOA нет, допускается отдельный настроенный NegativeTTL.
- Не кэшировать временные ошибки upstream (сетевые ошибки, SERVFAIL/REFUSED и другие ответы, которые должны привести к следующей попытке).

**Разделение и инвалидирование кэша:**

- Кэш режима 1 и кэш режима 2 должны иметь независимые namespace/generation.
- Generation режима 1 привязывается к текущему выбору ActiveDoHSelector и набору endpoint IP. При смене активного DoH, изменении endpoint IP или истечении freshness generation режима 1 меняется; записи режима 1 инвалидируются.
- Смена активного DoH не должна очищать кэш режима 2: его результаты не зависят от выбранного endpoint режима 1.
- Изменение списка/параметров upstream режима 2 инвалидирует кэш режима 2. Общая перезагрузка конфигурации может очищать весь кэш, как это уже делается в текущем runtime.
- Запрос, начатый со старым generation/snapshot, не должен повторно заполнить уже инвалидированный кэш.

**Что уже найдено в коде:**

- В `feature/auto-hosts-v3/cache.go` есть ограниченный по размеру DNS-кэш, singleflight для одинаковых запросов, сохранение DNS-пакета, восстановление transaction ID и уменьшение TTL при выдаче.
- В v3 TTL положительных ответов определяется минимальным TTL RR; отрицательный TTL берётся из SOA по RFC 2308, а при отсутствии SOA может использоваться NegativeTTL. MinTTL не повышает TTL, а запрещает кэширование слишком коротких ответов; MaxTTL ограничивает срок сверху.
- В v3 reload очищает существующий кэш и не даёт запросу от старого snapshot повторно наполнить его после reload.
- В текущем коде ещё нет двух новых DNS-режимов, отдельных cache namespace для них или инвалидирования режима 1 при событии смены ActiveDoHSelector. Это требования целевой архитектуры, а не уже реализованная функциональность.

Численные значения TTL и ограничения кэша пока не фиксируются: их следует определить в конфигурации и проверить на интеграционных сценариях.

### 4.4. CNAME, HTTPS/SVCB, DNSSEC и EDNS

**Режим 2 — прозрачная передача DNS:**

- Плагин передаёт DNS-пакет upstream и возвращает DNS-ответ без самостоятельного переписывания CNAME-цепочек, HTTPS/SVCB или DNSSEC-данных.
- Поддержка CNAME, HTTPS (QTYPE 65), SVCB (QTYPE 64), A/AAAA и других QTYPE должна обеспечиваться прозрачной передачей ответа upstream, а не собственным неполным парсером этих RR.
- EDNS-поля запроса должны сохраняться при передаче upstream. Не следует самостоятельно удалять или модифицировать клиентские опции в обычном upstream-пути.
- Плагин не реализует DNSSEC-валидатор. Он не должен самостоятельно устанавливать AD; флаг и DNSSEC-данные upstream передаются без самовольного изменения. Доверие к AD остаётся ответственностью настроенного upstream и клиента.

**Режим 1 — синтетический endpoint-ответ:**

- Плагин формирует A/AAAA ответы из адресов выбранного DoH endpoint-а, а не из DNS-ответа о запрошенном сайте.
- CNAME, HTTPS/SVCB и прочие RR не должны приводить к обычному разрешению исходного имени или утечке его реальных записей. Для QTYPE, отличных от A/AAAA, целевое поведение — NODATA; это необходимо проверить на реальных клиентах.
- Синтетический ответ не подписан DNSSEC. AD не устанавливается.
- Если запрос содержит EDNS OPT, синтетический ответ может сохранить согласованные базовые параметры (в частности UDP payload size и DO bit), но не должен отражать клиентские COOKIE, ECS и прочие payload options.

**Ограничение текущей реализации:** код v3 содержит инструменты разбора DNS wire, TTL и SOA, обработку EDNS OPT для локально сформированных ответов и защитную проверку CNAME-цепочек Auto Hosts. Это не полноценная DNSSEC-валидация и не отдельная реализация авторитетной обработки HTTPS/SVCB. Целевой дизайн использует прозрачную передачу для режима 2 и минимальную синтетическую A/AAAA-логику для режима 1.

## 5. Выбор одного активного DoH по восьми проверкам

Пользователь выбрал направление: **выделить из feature/auto-hosts-v3 самостоятельный алгоритм выбора одного активного DoH-сервера по восьми проверкам**.

В качестве отправной точки рассмотреть код:

- [autohosts_controller.go в feature/auto-hosts-v3](https://github.com/agentnht/doh-health-monitor/blob/feature/auto-hosts-v3/autohosts_controller.go);
- [bootstrap resolver в main.go](https://github.com/agentnht/doh-health-monitor/blob/main/main.go).

В контроллере v3 уже есть существенная часть необходимой логики:

1. Перебор настроенных DoH upstream (с исключением системного DNS из кандидатов на роль DoH).
2. Независимая проверка каждой пары «DoH-сервер × контрольный домен».
3. DNS A/AAAA запрос непосредственно через проверяемый DoH.
4. Получение IP сайта как временной цели проверки.
5. HTTPS-проверка непосредственно по полученному IP с исходным hostname, TLS SNI, HTTP Host и проверкой сертификата.
6. Ограничение параллелизма, таймауты и фильтрация недопустимых IP.
7. Оценка результатов и выбор одного активного кандидата.
8. Anti-flap: пороги повторных результатов, minimum hold и switch cooldown.
9. Ручной Pinned/Auto режим в существующей реализации.

Восемь контрольных доменов, используемые в v3:

- chatgpt.com
- claude.ai
- gemini.google.com
- elevenlabs.io
- grok.com
- www.perplexity.ai
- notebooklm.google.com
- aistudio.google.com

Планируется извлечь из v3 именно самостоятельный компонент выбора активного DoH — условно \`ActiveDoHSelector\`. Он должен выдавать согласованное состояние активного сервера и его endpoint, не управляя пользовательским списком доменов.

Предполагаемые данные результата:

- ID активного DoH-сервера;
- исходный URL/hostname;
- endpoint IPv4 и IPv6;
- время последнего успешного разрешения/обновления endpoint;
- состояние/возраст endpoint и причина выбора.

Это целевой интерфейс для обсуждения, не утверждённая структура Go-типа.

### Важное отличие от текущего main

В main уже существуют health monitor, выбор активного upstream по группам и bootstrap resolver, который разрешает hostname DoH-сервера в IP и тестирует IP-кандидаты.

Однако обычный активный upstream группы и **единственный активный DoH endpoint** — не обязательно одно и то же. В стандартной конфигурации группы может присутствовать системный DNS. Поэтому новую логику следует выделить отдельно и не считать текущий \`active[group]\` готовой заменой активного DoH-сервера.

## 6. Что можно повторно использовать из feature/auto-hosts-v3

### Кандидаты на перенос после отдельного аудита

- Алгоритм проб и выбора активного DoH из \`autohosts_controller.go\` — извлечь независимую часть, отвязав её от Auto Hosts manager.
- DNS wire исправления из \`dns_wire.go\` — выбирать необходимые изменения и переносить с их тестами.
- Ограниченный DNS cache и singleflight из \`cache.go\` — только если кэш останется в новой схеме и будет проверена совместимость с переключением endpoint/режима.
- Panic recovery DNS request boundary и соответствующие тесты.
- Ужесточения безопасности Web UI и status API, если они не завязаны на Auto Hosts.
- Усиления API-интеграции LucX-UI из \`internal/dohintegration/api.go\` — после проверки совместимости с задачами нового PR.
- Отдельные тестовые сценарии и подходы к race detector, проверке DNS, SNI/Host, TLS и отказам.

### Что не переносить как архитектурную основу

- \`internal/autohosts/manager.go\` и его доменный список.
- Очередь добавления пользовательских QNAME.
- LastSeen/ExpiresAt и GC записей Auto Hosts.

## 8. Где будет находиться Geosite и когда менять панель

Целевое направление — передать сопоставление доменов Geosite на сторону панели/Xray, чтобы не поддерживать второй независимый matcher в плагине.

При этом механизм ещё нужно технически подтвердить:

- как именно LucX-UI/Xray применяет Geosite при выборе DNS upstream;
- можно ли выделить отдельный DNS-путь для Geosite HIT;
- как запросы вне этого правила направлять в fallback;
- как исключить повторный перехват локального запроса Xray к listener плагина;
- как сохранять пользовательские DNS-конфигурации и порядок правил.

**На начальном этапе конфигурацию панели допустимо править вручную.** Автоматизацию изменения панели, Integrate/DeIntegrate и соответствующие доработки плагина отложить на самый конец, после подтверждения рабочей DNS-схемы и её тестирования.

Иными словами, сначала проверить архитектуру на вручную подготовленной конфигурации. Только после того, как схема стабильно работает, решать, какие изменения панели стоит автоматизировать.

## 10. Что пока не разрешено считать решённым

После согласования режимов, fallback, TTL и базовых DNS wire-принципов остаются следующие технические вопросы:

- точная структура конфигурации режимов, независимых списков endpoint-ов режима 1, resolver-upstream-ов режима 2 и bootstrap-resolver-ов;
- точный механизм разделения DNS-потоков Geosite в Xray/LucX-UI: отдельные listeners/upstreams, порядок DNS/routing rules, fallback и отсутствие повторного перехвата;
- wire-представление `blackhole` на границе DNS listener/Xray и поведение клиентов при таком ответе;
- подтверждение поведения режима 1 для запросов QTYPE, отличных от A/AAAA, включая HTTPS/SVCB и CNAME;
- проектирование и тестирование защиты от DNS-петли, если системный resolver ОС сервера указывает обратно на listener плагина;
- сетевой путь и bootstrap-разрешение hostname для DoH-upstream режима 2, включая проверку TLS SNI/Host и обработку нескольких IP;
- конкретные численные параметры TTL/cache и пределы freshness после измерений на интеграционных сценариях;
- решение о необходимости и объёме последующей автоматизации конфигурации панели/Xray.

Решения по fallback, TTL, кэшированию и общему DNS RR-подходу уже зафиксированы в разделе 4. Перечисленные выше пункты требуют технической проверки, уточнения конфигурационной схемы или интеграционного тестирования; это не отменяет согласованную семантику режимов.

До прохождения технической проверки не начинать автоматизацию панели и не переносить крупные части v3 целиком.

4. В браузер token передаётся только в URL fragment (#access_token=...), не в query string.
5. webui/app.js считывает fragment и немедленно удаляет его из адресной строки через history.replaceState, до первого запроса к приватным API.
6. JavaScript отправляет token на POST /session/exchange. Сервер принимает его только один раз, защищает проверку от конкурентного повторного использования и после успешного обмена очищает сохранённое значение launch token.

Это один согласованный security change через scripts/plugin-management.sh, webui.go, webui/app.js и тесты. Не переносить только часть обмена: иначе можно получить либо неработающий вход, либо незакрытый доступ к приватным API.

### 12.3. Приоритет P1 — аутентификация внутреннего daemon API

Эта задача связана с Web UI security, но отличается от браузерной сессии. Нужны две независимые границы доверия:

**Обязательная адаптация под новую архитектуру:** в v3 токен называется auto-hosts-api.token, а middleware/маршруты имеют имена requireAutoHostsAPIToken и /autohosts/.... Не переносить эти имена и Auto Hosts routes буквально. Для нового решения использовать нейтральное имя, например daemon-api.token, и общий middleware для тех endpoint, которые действительно остаются. Сам код защиты и проверку peer address можно переиспользовать; Auto Hosts handlers переносить не нужно.

Проверки: нет токена → 401; неверный формат/значение → 401; непетлевой Host, Origin или RemoteAddr → отказ; корректный loopback Bearer → запрос проходит. Проверить каждый Go/Python/shell клиент и тестами доказать, что все они посылают токен. Cookie Web UI не должна давать доступ к daemon API, а daemon Bearer token не должен выдаваться браузеру.

### 12.6. Что не переносить из v3 как есть

Не переносить cherry-pick-ом или заменой целых файлов:

- Auto Hosts tab, настройки, Dry Run, pinned/automatic/emergency-off state;
- динамические QNAME records, LastSeen, ExpiresAt, GC и связанные cache/state модели;
- Geosite matcher/parser, выбор категорий внутри плагина и управление runtime Geosite index из UI;
- /autohosts/* API, Auto Hosts daemon token naming и соответствующие JS handlers;
- автоматический выбор/сохранение пары DNS listener ports и dns-listener.json;
- Quad9 routing implementation, если ответственность за fallback будет закреплена за Xray/panel;
- весь daemon.go, webui.go, webui_admin.go, webui/app.js или webui/index.html из v3 без разборки.

Особенно важно: v3 Web UI файлы смешивают общую функциональность управления плагином с Auto Hosts/Geosite. Переносить отдельные согласованные изменения и тесты в текущие файлы main, сохраняя их существующие страницы и API.

### 12.7. Рекомендуемый порядок переноса и зависимости

1. **Shell hardening:** UID-фильтр и запуск только packaged checker. Проверить состав ZIP и shell-сценарии. Это наименее связанный с остальной работой этап.
2. **Одноразовый Web UI login:** согласованно перенести Go file/token flow, shell handoff, JS bootstrap и session exchange. Включить тесты сервера и браузерной bootstrap-логики в тот же change set.
3. **Daemon Bearer auth:** сначала определить имя и формат token file, затем защитить /status, после чего одним этапом обновить Go, Python и shell clients. Не выпускать промежуточное состояние, в котором сервер уже требует токен, а клиенты его ещё не посылают.
4. **Log redaction и DNS test validation:** отдельные небольшие изменения со своими unit tests.
5. **Reload/cache и фактический listener diagnostics:** только после того, как новая конфигурация DNS режимов и listener lifecycle определены.

Минимальный набор проверок после переноса:

- bash -n scripts/plugin-management.sh scripts/check-dns-integration.sh;
- node --check webui/app.js;
- gofmt для изменённых Go-файлов, go test ./... и go vet ./...;
- тесты одноразового launch token: успешный обмен, повторный обмен отклонён, token очищен из URL до первого API fetch, секрет отсутствует в stdout и query string;
- тесты cookie: cookie отдельная от launch token, HttpOnly, SameSite=Strict, все приватные routes требуют корректную сессию;
- тесты daemon API: отсутствующий/неверный Bearer, некорректная схема, не-loopback Host/Origin/RemoteAddr и корректный запрос;
- тесты Go/Python/shell клиентов, подтверждающие чтение защищённого token file и передачу Bearer;
- тесты redaction и безопасной передачи QNAME в dig;
- проверка, что management script и checker присутствуют в реальном release ZIP;
- затем отдельная проверка на VPS: SSH tunnel, открытие/закрытие Web UI, доступность UDP и TCP DNS listener и фактический статус после перезапуска.

CI и unit tests не заменяют VPS-проверку.

**Статус этого плана:** это список для последующего выборочного переноса, а не выполненный перенос кода. Cherry-pick всего PR #10 или замена файлов из v3 не рекомендуются. Сначала переносить P1-блоки небольшими согласованными наборами с тестами; изменения конфигурации панели и автоматизацию Xray по-прежнему оставить на последний этап.

# Концепция: Geosite DNS routing и режимы работы DoH

**Дата фиксации обсуждения:** 2026-11-19  
**Статус:** архитектурное обсуждение; это не утверждённое ТЗ реализации и не разрешение на изменение кода.  
**Базовая точка для будущей реализации:** ветка \`main\`, версия 2.2.1.

## 1. Цель обсуждения

Рассматривается отказ от Auto Hosts как отдельного динамического списка доменов и перенос определения Geosite-попаданий на сторону LucX-UI/Xray — туда, где уже находятся правила маршрутизации.

Предполагаемое разделение ответственности:

- **LucX-UI/Xray** определяет по своим правилам, к какой DNS-ветке направить запрос.
- **Плагин** проверяет доступность настроенных DoH-серверов, выбирает активный DoH и обслуживает направленный к нему DNS-поток согласно выбранному режиму.
- **Quad9 или другой настроенный fallback** используется для обычного разрешения имён в тех случаях, которые определит выбранный режим и его конфигурация.

Основная цель — не дублировать внутри плагина список Geosite, если панель/Xray уже умеет определять соответствующие домены.

## 2. Как пришли к этой идее

В ходе обсуждения PR #10 возник вопрос: зачем нужен Auto Hosts, если Geosite уже содержит классификацию доменов?

Рассматривался вариант:

1. Панель/Xray сопоставляет домен с Geosite-правилами.
2. DNS-запрос, который попал под нужное правило, направляется на DNS listener плагина.
3. Плагин возвращает IP активного DoH endpoint.
4. Запрос, который не попал под правило, направляется в Quad9 либо иной явно настроенный fallback.

При таком подходе плагину не требуется динамически добавлять QNAME в Auto Hosts, хранить пользовательские домены, обновлять LastSeen/ExpiresAt и удалять устаревшие записи. Само правило попадания в нужную DNS-ветку определяется панелью/Xray.

Важное техническое условие: один общий DNS listener не получает от Xray отдельный признак «какое правило совпало». Поэтому панель/Xray должны действительно разделить потоки до передачи запроса плагину — например, направлять их в разные DNS upstream/listener или обеспечить иным проверенным способом. Нельзя считать, что сам DNS-пакет содержит информацию о сработавшем routing rule.

## 3. Два взаимоисключающих режима плагина

В последнем уточнении пользователь обозначил два разных функциональных режима. Они должны включаться конфигурацией и **не должны работать одновременно**.

### Режим A. Обычное разрешение / направление на resolver

В этом режиме DNS-результат остаётся реальным адресом запрошенного сайта. Направление запроса/разрешения может быть настроено на:

- прямое подключение (Direct);
- выбранный DoH-сервер.

Точное значение слов «редирект на прямое подключение» для DNS-пути и то, является ли Direct альтернативой выбранному DoH внутри одного режима или отдельной настройкой этого режима, требуется уточнить при проектировании конфигурации.

В этом режиме нельзя подменять DNS-ответ IP-адресом DoH endpoint: клиент должен получить обычный адрес целевого домена.

### Режим B. Возврат IP активного DoH endpoint

Это желаемый режим **по умолчанию**.

Плагин выбирает один активный DoH-сервер по результатам фоновых проверок и возвращает IP его endpoint в DNS-ответе для запросов, направленных в соответствующую ветку.

- Для A возвращается IPv4 endpoint.
- Для AAAA возвращается IPv6 endpoint.
- IP сайта, полученный во время probe, не является IP endpoint и не должен подменять его в DNS-ответе.
- Endpoint IP хранится отдельно от IP сайтов, которые используются для проверки.

В этом режиме пользовательский домен не нужно добавлять в Auto Hosts: принадлежность к нужному DNS-потоку уже определена правилами панели/Xray.

### Взаимоисключение

В конфигурации должен быть один активный режим. Переключение режима должно быть явным. Нельзя одновременно применять обычное разрешение реального IP и синтетический ответ с IP DoH endpoint к одному и тому же DNS-потоку.

Предварительная иллюстрация конфигурации (имена ключей и окончательная схема ещё не утверждены):

- \`dns_mode: endpoint_ip\` — режим возврата IP активного DoH endpoint; значение по умолчанию.
- \`dns_mode: resolver\` — обычное разрешение имени.
- В режиме resolver отдельная политика может выбирать Direct или выбранный DoH, если это подтвердится как нужная семантика.

Это пример для обсуждения, не готовый формат config.json.

## 4. Fallback — сохранить как функциональность

Пользователь отдельно отметил, что fallback-функциональность желательно сохранить.

В частности, предыдущая реализация PR #10 использовала отдельный upstream \`vps-resolve\` с Quad9 Secure DoH:

\`https://dns.quad9.net/dns-query\`

Новая архитектура не должна случайно потерять fallback только из-за отказа от Auto Hosts. При этом необходимо отдельно определить, кто именно выполняет fallback — Xray/панель или Go-плагин — и для каких ошибок он применяется.

Требуется согласовать поведение как минимум в следующих ситуациях:

- активный DoH-сервер не выбран;
- endpoint IP не получен, устарел или больше не считается пригодным;
- нет адреса требуемого семейства (например, IPv4 есть, IPv6 отсутствует);
- выбранный DoH не отвечает или возвращает ошибку;
- плагин недоступен;
- запрос не попал под Geosite-правило.

Нужно сохранить различие между транспортной ошибкой DoH и валидным DNS-ответом с доменным RCODE. Нельзя автоматически считать NXDOMAIN/SERVFAIL конкретного домена доказательством того, что весь DoH upstream недоступен.

Точная матрица fallback для двух режимов пока **не утверждена**. В частности, надо решить, должен ли режим endpoint_ip при отсутствии пригодного endpoint разрешать исходное имя через Quad9, либо в некоторых случаях отвечать ошибкой/NODATA. Это важная часть спецификации, а не деталь реализации.

## 5. Выбор одного активного DoH по восьми проверкам

Пользователь выбрал направление: **выделить из feature/auto-hosts-v3 самостоятельный алгоритм выбора одного активного DoH-сервера по восьми проверкам**.

В качестве отправной точки рассмотреть код:

- [autohosts_controller.go в feature/auto-hosts-v3](https://github.com/agentnht/doh-health-monitor/blob/feature/auto-hosts-v3/autohosts_controller.go);
- [bootstrap resolver в main.go](https://github.com/agentnht/doh-health-monitor/blob/main/main.go).

В контроллере v3 уже есть существенная часть необходимой логики:

1. Перебор настроенных DoH upstream (с исключением системного DNS из кандидатов на роль DoH).
2. Независимая проверка каждой пары «DoH-сервер × контрольный домен».
3. DNS A/AAAA запрос непосредственно через проверяемый DoH.
4. Получение IP сайта как временной цели проверки.
5. HTTPS-проверка непосредственно по полученному IP с исходным hostname, TLS SNI, HTTP Host и проверкой сертификата.
6. Ограничение параллелизма, таймауты и фильтрация недопустимых IP.
7. Оценка результатов и выбор одного активного кандидата.
8. Anti-flap: пороги повторных результатов, minimum hold и switch cooldown.
9. Ручной Pinned/Auto режим в существующей реализации.

Восемь контрольных доменов, используемые в v3:

- chatgpt.com
- claude.ai
- gemini.google.com
- elevenlabs.io
- grok.com
- www.perplexity.ai
- notebooklm.google.com
- aistudio.google.com

Планируется извлечь из v3 именно самостоятельный компонент выбора активного DoH — условно \`ActiveDoHSelector\`. Он должен выдавать согласованное состояние активного сервера и его endpoint, не управляя пользовательским списком доменов.

Предполагаемые данные результата:

- ID активного DoH-сервера;
- исходный URL/hostname;
- endpoint IPv4 и IPv6;
- время последнего успешного разрешения/обновления endpoint;
- состояние/возраст endpoint и причина выбора.

Это целевой интерфейс для обсуждения, не утверждённая структура Go-типа.

### Важное отличие от текущего main

В main уже существуют health monitor, выбор активного upstream по группам и bootstrap resolver, который разрешает hostname DoH-сервера в IP и тестирует IP-кандидаты.

Однако обычный активный upstream группы и **единственный активный DoH endpoint** — не обязательно одно и то же. В стандартной конфигурации группы может присутствовать системный DNS. Поэтому новую логику следует выделить отдельно и не считать текущий \`active[group]\` готовой заменой активного DoH-сервера.

## 6. Что можно повторно использовать из feature/auto-hosts-v3

### Кандидаты на перенос после отдельного аудита

- Алгоритм проб и выбора активного DoH из \`autohosts_controller.go\` — извлечь независимую часть, отвязав её от Auto Hosts manager.
- DNS wire исправления из \`dns_wire.go\` — выбирать необходимые изменения и переносить с их тестами.
- Ограниченный DNS cache и singleflight из \`cache.go\` — только если кэш останется в новой схеме и будет проверена совместимость с переключением endpoint/режима.
- Panic recovery DNS request boundary и соответствующие тесты.
- Ужесточения безопасности Web UI и status API, если они не завязаны на Auto Hosts.
- Усиления API-интеграции LucX-UI из \`internal/dohintegration/api.go\` — после проверки совместимости с задачами нового PR.
- Отдельные тестовые сценарии и подходы к race detector, проверке DNS, SNI/Host, TLS и отказам.

### Что не переносить как архитектурную основу

- \`internal/autohosts/manager.go\` и его доменный список.
- Очередь добавления пользовательских QNAME.
- LastSeen/ExpiresAt и GC записей Auto Hosts.
- \`autoHostsEndpointResponse\` как механизм, зависящий от наличия домена в Auto Hosts.
- Geosite matcher/parser из \`internal/geosite/\`, если Geosite полностью обслуживается правилами панели/Xray.
- Auto Hosts UI, API и настройки, не нужные для новой архитектуры.
- Весь \`daemon.go\` без разборки: он включает инициализацию Auto Hosts, Geosite и Quad9, поэтому переносить его целиком нецелесообразно.

DNS wire, кэш и security fixes из v3 не считаются автоматически принятыми только потому, что они присутствуют в ветке. Каждый перенос требует проверки diff, соответствующих тестов и регрессии.

## 8. Где будет находиться Geosite и когда менять панель

Целевое направление — передать сопоставление доменов Geosite на сторону панели/Xray, чтобы не поддерживать второй независимый matcher в плагине.

При этом механизм ещё нужно технически подтвердить:

- как именно LucX-UI/Xray применяет Geosite при выборе DNS upstream;
- можно ли выделить отдельный DNS-путь для Geosite HIT;
- как запросы вне этого правила направлять в fallback;
- как исключить повторный перехват локального запроса Xray к listener плагина;
- как сохранять пользовательские DNS-конфигурации и порядок правил.

**На начальном этапе конфигурацию панели допустимо править вручную.** Автоматизацию изменения панели, Integrate/DeIntegrate и соответствующие доработки плагина отложить на самый конец, после подтверждения рабочей DNS-схемы и её тестирования.

Иными словами, сначала проверить архитектуру на вручную подготовленной конфигурации. Только после того, как схема стабильно работает, решать, какие изменения панели стоит автоматизировать.

## 9. Предлагаемый порядок дальнейшей работы

1. Уточнить точную семантику двух режимов и их взаимоисключение.
2. Определить матрицу fallback отдельно для каждого режима.
3. Проверить реальные DNS-возможности и конфигурацию целевой версии Xray/LucX-UI.
4. Определить способ разделения потоков: Geosite-попадания и все остальные DNS-запросы.
5. Выделить из v3 отдельный алгоритм выбора одного активного DoH на основе восьми проверок.
6. Определить формат состояния активного DoH endpoint и его freshness.
7. Создать новую рабочую ветку непосредственно от main и отдельный Draft PR.
8. Сначала реализовать и проверить DNS-поведение с ручной конфигурацией панели.
9. Добавить регрессионные, интеграционные и нагрузочные тесты, включая UDP/TCP, A/AAAA, DNS-ошибки, fallback, переключение DoH, cache и аварии listener.
10. В самом конце рассмотреть автоматизацию конфигурации LucX-UI/Xray, если она действительно необходима и может быть выполнена безопасно.

Предлагаемое имя новой ветки: \`feature/geosite-dns-routing\`. Это рекомендация; ветка ещё не создана.

## 10. Что пока не разрешено считать решённым

Следующие вопросы остаются открытыми:

- окончательные имена и структура параметров конфигурации режимов;
- является ли Direct отдельной политикой внутри режима обычного resolver или самостоятельным вариантом режима;
- точная семантика fallback для каждой ошибки и каждого режима;
- поведение при отсутствии IPv4/IPv6 endpoint;
- поведение для CNAME, HTTPS/SVCB, DNSSEC/DO и EDNS;
- допустимый TTL и согласование TTL с endpoint freshness и кэшированием;
- точный механизм Geosite DNS routing в целевой версии Xray;
- сетевой путь соединения к выбранному DoH endpoint и к Quad9;
- необходимость и объём последующей автоматизации панели.

До согласования этих вопросов не начинать перенос крупных частей v3 и не менять текущую архитектуру PR #10.

## 11. Ограничения и границы изменений

- Новую реализацию начинать от чистой ветки main, а не от feature/auto-hosts-v3.
- PR #10 оставить отдельной исторической веткой; не сливать его как основу новой архитектуры.
- Не переносить Auto Hosts целиком.
- Не менять main/manifest version 2.2.1 до прохождения необходимых проверок и отдельного release gate.
- Не считать CI заменой VPS-проверки.
- До отдельного согласования не менять рабочую конфигурацию панели.
- Автоматизацию LucX-UI/Xray отложить до конца; ранний прототип допускает ручную настройку панели.

---

**Итог текущего обсуждения:** новая архитектура должна использовать правила Geosite на стороне панели/Xray, независимый алгоритм выбора одного активного DoH по восьми проверкам и два взаимоисключающих DNS-режима с сохранением fallback. Режим возврата IP активного DoH endpoint предлагается сделать режимом по умолчанию. Реализация и автоматизация панели пока не начаты.

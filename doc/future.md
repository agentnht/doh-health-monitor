# Future work

## Более содержательные проверки доступности сервисов в Auto Hosts

**Статус:** идея для будущего обсуждения. Не является обязательной частью текущего плана Auto Hosts 3.0 и не должна автоматически расширять PR #10.

### Наблюдение

Сейчас контрольные probe Auto Hosts в первую очередь подтверждают техническую доступность пути через конкретный DoH-upstream: DNS-разрешение A/AAAA, HTTPS-подключение к полученному IP с исходными Host и TLS SNI, проверка сертификата и HTTP-условий.

Но успешный HTTP-ответ, в том числе 200, сам по себе не всегда означает, что пользователю доступна функция сервиса. Сервис может вернуть страницу или API-ответ с сообщением о региональном ограничении либо запрете доступа.

### Рекомендация

При отдельном проектировании следующего этапа рассмотреть расширение probe от проверки **транспортной доступности** к проверке **функциональной доступности сервиса**:

1. Сохранить существующую цепочку Auto Hosts: DNS через проверяемый DoH → подключение к разрешённому IP → HTTPS с исходными Host/SNI и проверкой сертификата.
2. Для отдельных контрольных доменов предусмотреть настраиваемые проверки HTTP status и содержимого ответа (например, наличие/отсутствие характерного признака региональной блокировки).
3. Там, где это возможно и устойчиво, использовать специализированные публичные API/endpoints вместо одной только главной страницы.
4. Различать транспортную ошибку, HTTP-ошибку, rate limit и явный отказ самого сервиса. Не трактовать любой HTTP 4xx/5xx или любой ответ API как доказательство неисправности DoH-upstream: часть таких ответов может быть общей ошибкой сервиса, приложения или конфигурации.
5. Не считать HTTP 200 безусловным признаком функциональной доступности.
6. Включать специальные проверки только для тех сервисов, где известны стабильный endpoint и однозначные критерии ответа. Не требовать авторизации пользователя и не выполнять платные/изменяющие состояние операции.

### Граница изменений

Это предложение для будущего обсуждения, а не поручение менять текущую реализацию. До отдельного согласования не менять:

- DNS priority и поведение DNS-ответов;
- алгоритм выбора активного DoH-upstream, anti-flap и Emergency OFF;
- набор восьми контрольных доменов и их смысл;
- пользовательский QNAME flow;
- Xray routing, Integrate/DeIntegrate и клиентские правила.

### Источник для изучения

- [XaksFlaX/ipregion-fixed — ipregion.sh](https://raw.githubusercontent.com/XaksFlaX/ipregion-fixed/refs/heads/main/ipregion.sh)

В скрипте полезен сам подход: общая HTTP-функция выполняет запросы с ограничениями времени/повторами, а отдельные функции для YouTube, ChatGPT, Claude, Netflix, Disney+, Reddit и Spotify интерпретируют ответы с учётом конкретного сервиса. Это позволяет отличать сетевую доступность от доступности сервиса или его функции. При повторном использовании подхода следует заново проверить актуальные endpoints и правила ответов: они могут меняться.

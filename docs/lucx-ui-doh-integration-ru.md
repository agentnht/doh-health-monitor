# Интеграция LucX-UI и DoH Health Monitor

Документ описывает интеграцию и удаление DoH Health Monitor 2.0.1 через API LucX-UI. Для работы существуют только две директивы: Integrate и Remove; каждая строит план по текущей конфигурации панели. Документ не является разрешением на изменение рабочей панели.

## Проверенная целевая среда

Во время предыдущей проверки панель сообщала версию 3.11.0-lucx.357 (/usr/local/x-ui/x-ui -v). Исходный код соответствующего тега LucX-UI был изучен для определения поведения API и сохранения Xray-настроек. Контрольная сумма установленного бинарного файла записывалась отдельно; репозиторий не утверждает, что бинарный файл VPS криптографически сопоставлен с этим тегом.

Зафиксированные параметры тестовой установки:

- DNS listener: 127.0.0.1:5355, UDP и TCP.
- Status API: http://127.0.0.1:18765/status.
- systemd unit: lucx-plugin-doh-health-monitor.
- Runtime-конфигурация Xray: /usr/local/x-ui/bin/config.json.
- База SQLite LucX-UI: /etc/x-ui/x-ui.db.
- Шаблон Xray хранится в настройке settings.xrayTemplateConfig.

Ранее оператор сообщал о результате проверки runtime-интеграции: 8 OK, 0 WARN, 0 FAIL. Также наблюдался цикл health-check без ошибок запросов. Это сообщения оператора о конкретном VPS, а не утверждения, подтверждённые CI.

## Инварианты шаблона Xray

В исследованном шаблоне уже присутствовал нужный DNS outbound:

```json
{
  "tag": "dns-out",
  "protocol": "dns",
  "settings": {
    "rewriteNetwork": "udp",
    "rewriteAddress": "127.0.0.1",
    "rewritePort": 5355
  }
}
```

В постоянную DNS-интеграцию входят DNS-сервер 127.0.0.1:5355 и глобальное правило TCP/UDP для порта 53 с направлением в dns-out. Loopback allow-исключение в `direct.settings.finalRules` — только временный диагностический ресурс, не часть постоянного плана.

Инструменты интеграции должны сохранять следующие свойства:

1. TCP/UDP запросы на порт назначения 53 должны идти через dns-out.
2. Локальное исключение xui-dns-allow должно оставаться перед блокировкой приватных IP.
3. Необходимо сохранять dns-doqd и все остальные пользовательские outbounds и routing rules.
4. Для интеграции через loopback не нужно добавлять firewall-правила REDIRECT.
5. Список доменов health-check не является allowlist для QNAME. Проверки оценивают доступность upstream; любой пользовательский запрос, попавший на локальный DNS listener, разрешается через выбранный upstream (с учётом явно заданных локальных переопределений).

Шаблон Xray не обязательно совпадает с полной runtime-конфигурацией. LucX-UI может добавлять специальные AWG outbounds, subscription outbounds и sidecar outbounds во время запуска. Нельзя заменять весь шаблон или считать, что все runtime outbounds присутствуют в xrayTemplateConfig.

## API LucX-UI и особенности перезапуска

Для изученной версии исходного кода:

- POST /panel/api/xray/ возвращает настройки Xray. В ответе содержится xraySetting в виде JSON-строки или объекта, а также метаданные, сформированные панелью.
- POST /panel/api/xray/update принимает сериализованный xraySetting, проверяет и нормализует его через SaveXraySetting, сохраняет xrayTemplateConfig и запускает механизм перезапуска/согласования Xray, если ядро работает.
- Механизм hot-diff поддерживает секции Xray API reload (inbounds, outbounds, routing rules/balancers). DNS-настройки в этот перечень не входят, поэтому их изменение может потребовать полного перезапуска процесса Xray.

До чтения Xray-настроек production-адаптер обязательно проверяет DoH Health Monitor: systemd-служба должна быть установлена и активна, TCP и UDP listener на loopback-порту 5355 должны работать, а локальный `/status` должен возвращать JSON-объект. Значения по умолчанию соответствуют конфигурации плагина; имя службы, status URL и порт можно задать параметрами. Если плагин отсутствует/остановлен или listener/status API не работают, адаптер прекращает выполнение до любого обращения к API панели.

Production-адаптер не запрашивает Bearer-токен у оператора. Он ищет `XUI_API_TOKEN` в защищённом `/etc/x-ui/install-result.env` (mode 0600), затем использует собственный сохранённый credential из `--panel-auth-file`; при отсутствии обоих вариантов обнаруживает исполняемый файл работающей панели и через штатную CLI LucX-UI создаёт отдельный токен `doh-health-monitor-integration` со scope `admin`. Токен сохраняется в `/var/lib/doh-health-monitor-panel-auth/panel-api-auth.json` с правами 0600; другие имена токенов не перевыпускаются. Создание токена затрагивает только хранилище API-токенов панели, не шаблон Xray. Если установленная CLI не поддерживает безопасный выпуск отдельного токена, адаптер останавливается без запроса секрета. Переменная окружения `XUI_API_TOKEN` может быть задана системой развёртывания. Адаптер никогда не записывает SQLite-базу панели напрямую и не изменяет runtime-конфигурацию Xray напрямую. Если `--base-url` не передан, адаптер читает только параметры `webPort`, `webBasePath`, `webCertFile`, `webKeyFile` и `webDomain` из локальной SQLite в режиме `mode=ro`, учитывая runtime-переопределение `XUI_PORT`. Сам web base path не выводится. TLS автоматически определяется по настройкам панели и SAN leaf-сертификата: без сертификата используется HTTP только через loopback; для IP SAN адаптер отправляет SNI `localhost`, сохраняет обязательную проверку доверенной цепочки и отдельно строго проверяет IP SAN; для DNS SAN использует доменное имя для стандартной проверки hostname и SNI. При явно заданном HTTPS `--base-url` нужно указать `--tls-mode ip --tls-name IP` или `--tls-mode domain --tls-name DOMAIN`; локальный HTTP можно явно выбрать через `--tls-mode http`. Проверка цепочки TLS не отключается ни в одном режиме. Для нестандартного расположения SQLite используется `--panel-db`, а для PostgreSQL или нестандартной установки — явный `--base-url`. Версия локального бинарного файла Xray определяется только для диагностики: неизвестная версия выводится как NOTICE и не блокирует Integrate/Remove. Если бинарный файл не найден, адаптер продолжает проверку совместимости по фактическому ответу API и структуре конфигурации. Версия LucX-UI выводится только для справки и не является жёстким ограничением совместимости. Совместимость определяется по фактическому поведению API и форме ответа, а не по жёсткому списку версий LucX-UI: адаптер должен успешно прочитать endpoint настроек Xray, разобрать `xraySetting`, сохранить метаданные `outboundTestUrl` и распознать структуру конфигурации. Неизвестные или отсутствующие поля приводят к остановке. Проверить endpoint записи без изменения состояния панели безопасно нельзя. Пользовательского режима `--plan-only` нет: команда выполняет выбранную директиву после построения и проверки плана. Если ответ API или структура конфигурации не распознаны, адаптер останавливается.

## Инструменты в этом PR

- \`scripts/check-dns-integration.sh\`: read-only проверка службы плагина, TCP/UDP listener, status API, DNS-сервера и активного правила порта 53 вместе с outbound, на который оно ссылается. Имя outbound не считается фиксированным.
- \`scripts/xray_dns_planner.py\`: общий чистый анализатор и планировщик. Он изучает inbound, outbound, DNS-серверы, routing rules, balancers и связанные теги в шаблоне Xray. Существующий DNS-outbound можно использовать независимо от его имени, только если фактическое назначение — \`127.0.0.1:5355/udp\`, а собственные DNS-правила и транспорт не перенаправляют/не блокируют запросы. Глобальный balancer подходит только тогда, когда все совпадающие по selector outbound и его \`fallbackTag\` ведут к совместимым DNS-outbound.
- Новые объекты добавляются только при необходимости. Перед созданием выбираются свободные теги outbound и routing \`ruleTag\`; учитываются теги inbound, outbound, balancer, API, DNS-приложения, DNS-серверов, существующих правил и даже незакрытых ссылок inbound/outbound/balancer. Также учитываются префиксы selector-ов балансировщиков и observatory. Дубли определённых тегов в пространствах имён Xray считаются неоднозначностью. Создаваемое правило ссылается на фактически выбранный outbound tag. Если \`dns-out\` уже занят другим назначением, существующий объект сохраняется, а для интеграции подбирается другое свободное имя. Пользовательские объекты и правила не переписываются ради совпадения.
- Анализ маршрутизации учитывает порядок первого совпадения и пересечения с портом 53. Более узкие пользовательские правила сохраняются перед общим fallback. Широкое правило/диапазон, которое перехватило бы трафик до нового правила, можно переиспользовать только если оно уже направляет его в полностью совместимый локальный DNS-target. Иначе планировщик останавливается с конфликтом, а не предлагает недостижимое правило. Отсутствующие или неоднозначные ссылки на outbound/balancer, а также неоднозначный выбор между несколькими совместимыми DNS-outbound являются блокирующими ошибками.
- \`scripts/lucx-ui-doh-api.py\`: API-адаптер панели. Его \`build_plan\` использует общий анализатор, а затем моделирует нормализацию \`xui-dns-allow\` самой LucX-UI, обязательное API-правило и известные побочные эффекты сохранения. Постоянные команды Integrate и Remove используют один desired-state план; диагностические команды Tunnel отделены от постоянной интеграции. Каждая запись проверяется повторным чтением через API.
- \`scripts/doh-integration-dry-run.py\` загружает тот же планировщик, что и API-адаптер; отдельной логики преобразования больше нет. \`scripts/doh-integration-staging.py\` копирует исходную SQLite-базу в отдельный staging-файл и поддерживает dry-run, verify, apply, rollback и cleanup только для staging-копии. Исходная/рабочая БД не изменяется.
- Отдельных CLI-команд для диагностического Tunnel нет. Внутренний диагностический lifecycle вызывается только из `integrate`: Tunnel и временное правило создаются/переиспользуются для UDP/TCP self-test, после чего автоматически очищаются по live-проверке внешних ссылок.
- Постоянная директива Integrate после применения desired-state плана создаёт диагностический Tunnel, если его ещё нет, и запускает UDP/TCP self-test. После любой попытки UDP/TCP self-test очистка выполняется независимо от результата теста. Для каждого диагностического inbound и `finalRule` анализируются внешние ссылки в текущей конфигурации: объект удаляется, только если вне диагностического плана он нигде не используется; в противном случае сохраняется. Маркеры `added/reused` и факт прежнего существования не определяют владение. Если тест и очистка завершаются ошибками, они сообщаются раздельно. Постоянная DNS-конфигурация остаётся применённой.
- Remove работает только с постоянным DNS-планом: маршрут порта 53, outbound и DNS server. Он проверяет внешние ссылки и удаляет только неиспользуемые ресурсы одной записью с последующим read-back. Inbound и `direct.settings.finalRules` он не анализирует и не изменяет: это диагностические ресурсы, которые обязан очистить Integrate после self-test. Их остаток означает ошибку диагностической очистки, а не задачу Remove.
- Изменение настроек панели может автоматически перезапустить Xray. Адаптер выводит NOTICE; интерактивного подтверждения и обязательного флага `--approve-restart` нет.
- Адаптер прекращает сохранение, если панель при нормализации DNS-исключения переместит/создаст внутреннее API-правило, преобразует числовой DNS \`qType: 0\` либо удалит/переставит пользовательское routing rule. Сохраняется метаданные \`outboundTestUrl\`, локальная авторизация разрешается автоматически, секреты не выводятся. Read-handler панели может самостоятельно исправлять старую обёрнутую форму \`xrayTemplateConfig\`; сам адаптер такую запись в БД не выполняет.

### Директива Remove

Удаление — отдельный выбор действия Remove, а не восстановление старой конфигурации. Адаптер строит актуальный план на основе текущих настроек панели, находит объекты интеграции по семантическим признакам и взаимосвязям, проверяет все ссылки и зависимости. Сначала удаляется подтверждённое интеграционное правило порта 53; после read-back заново проверяются ссылки, и только затем могут удаляться неиспользуемые outbound и DNS server. Общие, повторно используемые и неоднозначные объекты остаются.

Каждый вызов Integrate или Remove строит полный план по текущей конфигурации панели. Старые настройки целиком не восстанавливаются, пользовательские изменения не перезаписываются.

**Архитектурное требование:** новые версии адаптера не создают и не требуют полных снимков Xray до/после, копий старых массивов правил, обязательных recovery-журналов или отложенного snapshot-based rollback. Каждый API mutation проверяется повторным чтением и новым планом.

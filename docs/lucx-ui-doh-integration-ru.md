# Интеграция LucX-UI и DoH Health Monitor

Документ описывает интеграцию DoH Health Monitor 2.0.1 с панелью LucX-UI через её API, ограничения безопасного изменения настроек, проверку и откат. Он не является разрешением на изменение рабочей панели.

## Проверенная целевая среда

Во время предыдущей проверки панель сообщала версию 3.11.0-lucx.357 (/usr/local/x-ui/x-ui -v). Исходный код соответствующего тега LucX-UI был изучен для определения поведения API и сохранения Xray-настроек. Контрольная сумма установленного бинарного файла записывалась отдельно; репозиторий не утверждает, что бинарный файл VPS криптографически сопоставлен с этим тегом.

Зафиксированные параметры тестовой установки:

- DNS listener: 127.0.0.1:5355, UDP и TCP.
- Status API: http://127.0.0.1:18765/status.
- systemd unit: lucx-plugin-doh-health-monitor.
- Runtime-конфигурация Xray: /usr/local/x-ui/bin/config.json.
- База SQLite LucX-UI: /etc/x-ui/x-ui.db.
- Шаблон Xray хранится в настройке settings.xrayTemplateConfig.

Ранее оператор сообщал о результате проверки runtime-интеграции: 8 OK, 0 WARN, 0 FAIL. Также наблюдался цикл health-check без ошибок запросов. Это сообщения оператора о конкретном VPS, а не утверждения, подтверждённые CI.

## Инварианты шаблона Xray

В исследованном шаблоне уже присутствовал нужный DNS outbound:

```json
{
  "tag": "dns-out",
  "protocol": "dns",
  "settings": {
    "rewriteNetwork": "udp",
    "rewriteAddress": "127.0.0.1",
    "rewritePort": 5355
  }
}
```

В нём также были DNS-сервер 127.0.0.1:5355, глобальное правило TCP/UDP для порта 53 с направлением в dns-out и правило xui-dns-allow, разрешающее соединение с 127.0.0.1:5355 через direct. Разрешающее правило находилось перед блокирующим правилом geoip:private.

Инструменты интеграции должны сохранять следующие свойства:

1. TCP/UDP запросы на порт назначения 53 должны идти через dns-out.
2. Локальное исключение xui-dns-allow должно оставаться перед блокировкой приватных IP.
3. Необходимо сохранять dns-doqd и все остальные пользовательские outbounds и routing rules.
4. Для интеграции через loopback не нужно добавлять firewall-правила REDIRECT.
5. Список доменов health-check не является allowlist для QNAME. Проверки оценивают доступность upstream; любой пользовательский запрос, попавший на локальный DNS listener, разрешается через выбранный upstream (с учётом явно заданных локальных переопределений).

Шаблон Xray не обязательно совпадает с полной runtime-конфигурацией. LucX-UI может добавлять специальные AWG outbounds, subscription outbounds и sidecar outbounds во время запуска. Нельзя заменять весь шаблон или считать, что все runtime outbounds присутствуют в xrayTemplateConfig.

## API LucX-UI и особенности перезапуска

Для изученной версии исходного кода:

- POST /panel/api/xray/ возвращает настройки Xray. В ответе содержится xraySetting в виде JSON-строки или объекта, а также метаданные, сформированные панелью.
- POST /panel/api/xray/update принимает сериализованный xraySetting, проверяет и нормализует его через SaveXraySetting, сохраняет xrayTemplateConfig и запускает механизм перезапуска/согласования Xray, если ядро работает.
- Механизм hot-diff поддерживает секции Xray API reload (inbounds, outbounds, routing rules/balancers). DNS-настройки в этот перечень не входят, поэтому их изменение может потребовать полного перезапуска процесса Xray.

Production-адаптер обращается только к API панели после явного подтверждения оператора. Он не открывает и не записывает рабочую SQLite-базу и не изменяет runtime-конфигурацию Xray напрямую. Перед работой адаптер определяет версию локального бинарного файла Xray. Версия, которая ещё не проверялась на staging-панели, сопровождается предупреждением и требует отдельного подтверждения оператора. Версия LucX-UI выводится только для справки и не является жёстким ограничением совместимости. Если ответ API или структура конфигурации не распознаны, адаптер останавливается: безопасно предсказать результат сохранения в таком случае невозможно.

## Инструменты в этом PR

- scripts/check-dns-integration.sh: read-only проверки службы плагина, TCP/UDP listener, status API, DNS outbound/server/rules в runtime-конфигурации Xray.
- scripts/doh-integration-dry-run.py: автономный offline-планировщик. Он читает JSON fixture либо SQLite в read-only режиме и показывает, какие целевые поля staging-преобразование добавило бы. Он ничего не записывает и не является production API-адаптером.
- scripts/doh-integration-staging.py: копирует исходную SQLite-базу в отдельный staging-файл и поддерживает dry-run, verify, apply и rollback только для этого staging-файла. Это инструмент проверки на тестовых данных, а не рабочей базы панели.
- scripts/lucx-ui-doh-api.py: production-адаптер с добавочным характером изменений, использующий API LucX-UI. Он читает текущий шаблон, добавляет только отсутствующие dns-out, dns.servers: 127.0.0.1:5355 и глобальное правило TCP/UDP для порта 53. Существующие outbounds, DNS-серверы и пользовательские routing rules не редактируются и не удаляются. Правило порта 53 помещается сразу после внутреннего правила api -> api, поэтому применяется ко всем inbound-туннелям до пользовательских routing rules. Сам адаптер не создаёт xui-dns-allow: это исключение обрабатывает хук EnsureDnsServerRouting панели на основании локальных DNS endpoints.
- Перед сохранением API-адаптер проверяет, не будет ли панель дополнительно перемещать/создавать внутреннее API-правило, преобразовывать числовой DNS qType: 0 или удалять/переставлять существующие routing rules во время синхронизации DNS allow-правил. Предварительная проверка моделирует нормализацию панели с учётом новых DNS endpoints и старых allow rules, которые панель может принять под своё управление. Адаптер сохраняет метаданные outboundTestUrl, запрашивает Bearer API token скрытым вводом, не выводит секреты и создаёт резервные копии до/после с правами 0600. Для запуска требуются root-права на VPS с LucX-UI. API панели должен быть доступен локально по localhost или loopback. Версия Xray определяется по локальному бинарному файлу (или задаётся через --xray-bin). Если версия отсутствует в списке проверенных, выводится предупреждение и запрашивается подтверждение. Список проверенных версий остаётся пустым, пока конкретная версия ядра не пройдёт проверку на staging-панели. Версия LucX-UI показывается только как справочная информация.
- Обработчик чтения POST /panel/api/xray/ в обычной конфигурации не меняет настройки. Однако в изученной версии LucX-UI он может автоматически исправить старую обёрнутую форму xrayTemplateConfig, вызвав SaveXraySetting прямо во время чтения. Адаптер не записывает SQLite самостоятельно; в такой старой базе панель может выполнить внутреннее исправление в ходе своего API-запроса.
- Обновление DNS через POST /panel/api/xray/update может привести к полному перезапуску Xray, если ядро запущено. Для apply требуется явное подтверждение перезапуска. Режимы check и plan не отправляют обновление. Инструмент никогда напрямую не записывает SQLite-базу панели или runtime-конфигурацию Xray.
- tests/test_doh_integration.py и tests/test_lucx_ui_doh_api.py проверяют преобразования, обработку конфликтов, сохранение настроек, разбор ответов API и запросы к mock-панели без необходимости подключаться к реальной панели.

Не добавляйте в репозиторий рабочую базу панели или полный Xray config: они могут содержать приватные настройки, идентификаторы, учётные данные и пользовательские routing rules. Тесты должны использовать только минимальные синтетические данные.

## Ручная проверка, выполненная ранее

Во время разработки на частном VPS оператор сообщал о следующих действиях:

- чтение шаблона через SQLite в режиме только для чтения;
- dry-run на базе панели: изменений не предлагалось;
- dry-run на отдельном JSON fixture: изменений не предлагалось;
- тестирование преобразований при отсутствующих и некорректных DNS-элементах, дубликатах, конфликтах, сохранении несвязанных настроек и неизменности входных данных;
- проверка идемпотентности: повторное применение преобразования после исправления не предлагало новых изменений;
- создание staging-копии, dry-run и verify на отдельной копии: изменений не предложено, права файла 0600;
- цикл записи staging-данных на отдельной тестовой SQLite-копии: тестовое значение rewritePort=9999 было исправлено на 5355, проверка чтением прошла, rollback восстановил 9999, следующий dry-run снова предложил исправление. По сообщению оператора, рабочая база панели не затрагивалась.

Это результаты ручной проверки оператора на staging/test-копиях, а не запись в production. Автоматизированный набор тестов независимо проверяет тот же жизненный цикл на синтетических SQLite-файлах. Ни один из этих инструментов не выполняет обновление рабочей панели или перезапуск Xray без участия оператора.

# Auto Hosts — архитектурный план

**Статус:** согласованная концепция; реализация не входит в этот документальный этап.  
**Базовая версия проекта:** 2.2.1  
**Целевая ветка:** `feature/auto-hosts-design`

## 1. Назначение и ключевая семантика

Добавить в DoH DNS Gateway необязательную функцию Auto Hosts. Auto Hosts хранит только нормализованные доменные имена, которые успешно проверены через выбранный активный Smart DNS/DoH-сервер. IP активного DoH endpoint хранится отдельно в состоянии Active Smart DNS.

При DNS-запросе домена из Auto Hosts плагин возвращает IP активного DoH endpoint соответствующего семейства (A — IPv4, AAAA — IPv6). IP сайта, полученный при проверке через DoH, используется только для TCP/TLS/HTTP-проверки и никогда не записывается в Auto Hosts или в DNS-ответ клиенту.

**Логическая модель данных:**

- `auto_hosts`: множество доменных имён без IP-значений;
- `active_smart_dns`: ID выбранного DoH-сервера, его исходный URL/hostname и отдельно разрешённые IPv4/IPv6 endpoint;
- `probe_results`: результаты проверок для каждой пары «DoH-сервер × домен», включая временный IP сайта, статус, время и диагностику.

IP endpoint должен разрешаться отдельно от IP сайта. Для HTTPS-запросов к DoH сохраняются исходные URL hostname, TLS SNI, проверка сертификата и HTTP Host.

## 2. Алгоритм заполнения Auto Hosts

Список из восьми доменов заменяет прежние 25 health-check доменов. Каждый домен проверяется отдельно через каждый настроенный DoH endpoint; успешность одного домена не зависит от результатов остальных:

1. Фоновый монитор отправляет DNS-запрос контрольного домена непосредственно через проверяемый DoH endpoint, не используя локальный DNS listener плагина.
2. Получает IP сайта из DNS-ответа. Этот IP — временная цель проверки, он не является IP DoH endpoint.
3. Проверяет доступность сайта по TCP/TLS/HTTP с исходным доменом в SNI и HTTP Host; URL/path, ожидаемый статус и дополнительные критерии задаются тестовой записью.
4. Сохраняет результат отдельно для пары «DoH-сервер × домен». Успешная проверка домена через сервер A не означает, что этот домен доступен через сервер B.
5. Если домен успешно проверен через текущий активный сервер, его имя добавляется в Auto Hosts. Если проверка неуспешна, домен не добавляется (или сохраняется до окончания stale/grace, если ранее был подтверждён).
6. Не требуется, чтобы один DoH-сервер успешно прошёл все восемь доменов. Частичные результаты допустимы и ожидаемы.

IP самого DoH endpoint разрешается отдельно по hostname URL и хранится в `active_smart_dns`; он не копируется в каждую запись Auto Hosts. При HTTPS-проверках сохраняются исходные hostname URL, TLS SNI, сертификат и HTTP Host.

## 3. DNS-поведение Auto Hosts

При получении клиентского DNS-запроса:

1. Проверить ручной `local_hosts`; ручная запись имеет наивысший приоритет.
2. Если Auto Hosts выключен, продолжить существующий DNS Gateway pipeline без изменений.
3. Если Auto Hosts включён и домен присутствует в Auto Hosts, вернуть IP единственного активного DoH endpoint из отдельного состояния `active_smart_dns`. Все домены Auto Hosts в один момент времени используют один и тот же активный endpoint.
4. Если домена нет в Auto Hosts, использовать прежнее поведение DNS Gateway; заполнение Auto Hosts выполняется отдельным фоновым механизмом.
5. Для A возвращать IPv4 активного endpoint, для AAAA — IPv6. Если адреса соответствующего семейства нет, отвечать NODATA; не подменять AAAA-ответ IPv4-адресом.

Таким образом, Auto Hosts — именно динамический hosts-подобный список DNS-ответов, а не таблица выбора upstream для последующего разрешения пользовательского QNAME.

## 4. tst-domen.txt и предварительные проверки

Существующий `tst-domen.txt` развивается в список контрольных доменов и сценариев проверки пригодности DoH-серверов для этих доменов.

Базовый набор доменов берётся из проекта-примера HB AI (`Probe.Host`) без самовольного расширения:

| Домен | Назначение |
|---|---|
| `chatgpt.com` | ChatGPT |
| `claude.ai` | Claude |
| `gemini.google.com` | Gemini |
| `elevenlabs.io` | ElevenLabs |
| `grok.com` | Grok |
| `www.perplexity.ai` | Perplexity |
| `notebooklm.google.com` | NotebookLM |
| `aistudio.google.com` | Google AI Studio |

Именно этот набор из восьми доменов заменяет прежний список из 25 health-check доменов. Каждый домен проверяется независимо через каждый настроенный DoH-сервер; успешный результат одной проверки не требует успеха остальных семи. Список остаётся редактируемым через `tst-domen.txt`/Web UI; новые домены добавляются явно.

Для каждой пары «DoH-сервер × контрольный домен»:

- отправить DNS-запрос A/AAAA непосредственно на соответствующий DoH endpoint;
- получить все IP сайта из ответа;
- проверить IP сайта по TCP/TLS с исходными SNI и HTTP Host, URL/path, ожидаемым HTTP-статусом и дополнительными условиями;
- если конкретный домен успешно прошёл проверку через конкретный DoH endpoint, сохранить успешный результат этой пары;
- если конкретный домен успешно проверен через текущий активный endpoint, добавить/обновить только имя этого домена в Auto Hosts;
- IP сайта, полученные через DoH, использовать только в процессе проверки и не помещать в Auto Hosts;
- не требовать полного успеха всех восьми доменов для включения отдельного домена.

Предварительная проверка не является гарантией доступности для каждого пользователя: она выполняется с VPS и подтверждает доступность с VPS. Контрольный список не должен превращаться в жёсткий запрет для остальных доменов, если позднее будет добавлена проверка по запросу или расширение набора тестов.

Формат и миграция существующего `tst-domen.txt` должны быть обратно совместимыми. Старые записи продолжают работать в текущем health-check режиме; расширение формата и семантики согласовать до реализации, не меняя существующие поля молча.

## 5. Обновление и сохранность записей

- Не проверять все домены и все серверы на каждом DNS-запросе.
- Выполнять проверки по расписанию, при ручном запуске или по явно определённому событию обновления.
- Объединять параллельные проверки одной пары «домен × DoH-сервер» в одну операцию.
- Успешная повторная проверка обновляет timestamp последнего успеха и срок свежести записи.
- Единичная ошибка, timeout или временная недоступность DoH не удаляет ранее подтверждённый домен немедленно.
- У каждой записи должны быть как минимум timestamp последнего успешного probe и вычисляемый срок окончания grace. Неуспешные проверки не продлевают срок хранения: иначе запись могла бы оставаться в Auto Hosts бесконечно при постоянных сбоях.
- Если до истечения grace приходит успешная проверка через текущий активный сервер, запись обновляется и её срок хранения отсчитывается заново от нового успеха.
- После истечения grace без нового успешного подтверждения домен удаляется из опубликованного Auto Hosts и перестаёт получать синтетический endpoint IP.
- При смене активного сервера публиковать домены только по успешным и ещё действительным результатам именно нового активного сервера. Результат другого сервера не продлевает grace для текущего активного сервера.
- Параметры периода проверки и grace должны настраиваться раздельно; значения по умолчанию и допустимые диапазоны определить при реализации и покрыть тестами.
- Предусмотреть лимит размера списка, атомарную запись файла и очистку окончательно устаревших записей.

## 6. Хранилище, приоритеты и форматы

- Ручной `local_hosts` и Auto Hosts — разные хранилища.
- Ручной `local_hosts` всегда имеет приоритет над Auto Hosts.
- Auto Hosts хранится отдельно в `$LUCX_PLUGIN_DATA`.
- Auto Hosts хранит только нормализованные доменные имена, без IP-адресов.
- `active_smart_dns` отдельно хранит ID активного DoH-сервера, исходный URL/hostname и разрешённые IP endpoint (IPv4/IPv6).
- `probe_results` отдельно хранит состояние каждой пары «DoH-сервер × домен», время последней проверки, временные IP сайта и диагностику.
- Не сохранять IP сайта, полученный из DNS-ответа проверочного DoH-запроса, в Auto Hosts или в качестве IP активного endpoint.
- Если один DoH URL разрешается в несколько IP, хранить все допустимые адреса отдельно в состоянии endpoint; не терять hostname URL, необходимый для корректного HTTPS/SNI.
- В каждый момент времени активен один выбранный DoH endpoint; Auto Hosts не содержит доменно-зависимых пулов серверных IP.
- Запись и замена файла должны быть атомарными, чтобы сбой процесса не повреждал последнюю рабочую базу.

## 7. DNS-типы и ограничения

- Определить поведение A и AAAA отдельно: IP-адрес DoH endpoint может быть IPv4 и/или IPv6. Возвращать только адреса соответствующего семейства.
- Для типов, не поддерживаемых hosts-подобной записью (например, HTTPS/SVCB), сохранить согласованное безопасное поведение существующего DNS Gateway; не подменять их произвольными A/AAAA-ответами.
- Нормализовать домены, корректно обрабатывать завершающую точку и регистр.
- На первом этапе поддерживать точные доменные имена. Wildcard требует отдельного определения семантики и приоритетов.
- TTL Auto Hosts должен быть ограниченным и согласованным с периодом обновления; не выдавать бесконечный TTL.
- Не допускать рекурсивного обращения проверочного DoH-запроса к собственному DNS listener.

## 8. Wildcard

Wildcard не включать автоматически в первый этап. До его реализации определить:
- область действия правила и обработку apex-домена;
- приоритет точного совпадения над wildcard;
- распространяется ли IP DoH endpoint на все поддомены или для каждого фактического QNAME требуется отдельная проверка;
- как обновлять и удалять wildcard-записи без потери последней рабочей конфигурации.

## 9. Управление в Web UI

Добавить отдельный раздел Auto Hosts, не смешивая его с ручным `local_hosts` и редактором `tst-domen.txt`.

Предусмотреть:
- переключатель Auto Hosts (по умолчанию выключен);
- интервал проверок, таймауты и критерии доступности;
- период фоновой проверки (интервал между циклами);
- срок сохранения домена после последнего успешного подтверждения (stale/grace), независимый от периода проверки;
- отображение для каждой записи времени последнего успеха и оставшегося grace;
- лимит размера списка;
- таблицу доменов, включённых в Auto Hosts;
- отдельное отображение активного DoH-сервера и его IPv4/IPv6 endpoint;
- таблицу результатов проверок по парам «DoH-сервер × домен»;
- отображение времени последней проверки и состояния записи;
- просмотр диагностических результатов, включая IP сайта, использованные только для проверки;
- ручной запуск проверок и очистку динамического списка.

В UI и диагностике явно разделять три сущности: IP DoH endpoint, IP сайта из ответа DoH и IP, возвращаемый клиенту из Auto Hosts. В Auto Hosts и в DNS-ответе для домена используется именно IP DoH endpoint.

## 10. Совместимость и границы изменений

- Auto Hosts — отдельная опция, выключенная по умолчанию.
- При выключенной опции существующее поведение DNS Gateway не меняется.
- Не менять текущий алгоритм выбора основного DoH-upstream для обычных DNS-запросов.
- Не менять клиентские правила маршрутизации, Xray DNS integration и исходники LucX-UI.
- Проверочные запросы отправлять непосредственно к DoH endpoint, не через собственный DNS listener.
- Все новые настройки и файлы размещать в `$LUCX_PLUGIN_DATA`.
- Реализация и Web UI остаются внутри плагина.

## 11. Этапы реализации

1. Инвентаризировать DNS pipeline, DoH client, health-check parser/runner, `local_hosts`, cache, hot reload и Web UI API.
2. Заменить прежние 25 health-check доменов единым списком из восьми доменов; проверять каждую пару «DoH-сервер × домен» независимо, получать IP сайта и проверять его с исходными SNI/Host.
3. Реализовать отдельные хранилища Auto Hosts (только доменные имена), `probe_results` и `active_smart_dns` (ID/URL и IP endpoint), с атомарным обновлением и stale/grace.
4. Добавить DNS-ответы из Auto Hosts: ручной `local_hosts` приоритетнее; для Auto Hosts возвращать IP единственного активного DoH endpoint, хранящийся отдельно.
5. Реализовать единый фоновый контроллер выбора активного сервера и атомарную публикацию состояния; DNS-запросы не должны запускать проверки или переключение.
6. Добавить настройки и просмотр Auto Hosts в Web UI.
7. Добавить unit/integration tests: независимый успех/сбой каждой пары «DoH-сервер × домен» (без требования пройти весь набор), одинаковый активный endpoint для всех Auto Hosts доменов, атомарное обновление без частичных снимков, несколько DoH IP, несколько IP сайта, A/AAAA, SNI/Host, TTL, fallback, временный сбой, stale/grace, hot reload, параллельные проверки, выключенный режим и приоритет ручного `local_hosts`.
8. Обновить README, changelog, примеры конфигурации, manifest/version и CI.

## 12. Критерии приёмки

- При выключенном Auto Hosts старое поведение подтверждено регрессионными тестами.
- Проверочный DNS-запрос выполняется непосредственно через проверяемый DoH endpoint.
- IP сайта из DNS-ответа используется только для TCP/TLS/HTTP-проверки с исходными SNI и Host.
- Прежний список из 25 health-check доменов заменён набором из восьми доменов.
- Проверки каждой пары «DoH-сервер × домен» выполняются независимо; успех одного домена не зависит от остальных.
- Auto Hosts содержит только имена доменов, подтверждённо доступных через текущий активный сервер (с учётом stale/grace); для добавления отдельного домена не требуется успешная проверка остальных доменов.
- IP активного DoH endpoint хранится отдельно; запрос любого домена из Auto Hosts получает IP этого единственного endpoint, а не IP сайта.
- Несколько DNS-запросов не могут инициировать конкурирующие переключения активного сервера.
- Временная ошибка проверки не удаляет последнюю успешную запись.
- Ручной `local_hosts` имеет приоритет и не перезаписывается.
- Проверки не зацикливаются через собственный DNS listener.
- Изменения не требуют модификации LucX-UI или клиентских правил.
- Все новые данные хранятся отдельно в `$LUCX_PLUGIN_DATA` и записываются атомарно.

## 13. Вне объёма

- Изменение исходников LucX-UI.
- Изменение клиентских Xray/sing-box routing rules.
- Полноценный Smart DNS Rule Engine или таблица выбора upstream для каждого пользовательского DNS-запроса.
- FakeDNS.
- Автоматическая публикация/изменение конфигурации панели.
- Гарантия доступности приложения только на основании TCP/TLS/HTTP-проверки.


## 14. Особо важные требования к реализации

Этот раздел — обязательный инженерный чек-лист. Он уточняет архитектуру и не расширяет её функциональные границы.

### 14.1. Единый согласованный снимок состояния

- DNS-обработчик читает один неизменяемый snapshot: флаг Auto Hosts, выбранный сервер, endpoint IPv4/IPv6 и опубликованный набор доменов.
- Новый snapshot публикуется одной атомарной операцией только после проверки внутренней согласованности. Нельзя отдельно обновить активный сервер, а затем с задержкой список доменов или endpoint IP.
- При ошибке подготовки нового состояния сохраняется предыдущий last-known-good snapshot; нельзя публиковать пустой или частично собранный список.
- Не держать блокировки во время сетевых запросов и не выполнять проверки в критическом пути клиентского DNS-запроса.
- При выключении Auto Hosts DNS-путь обходит динамический список и сохраняет прежнюю обработку запросов.

### 14.2. Разделение endpoint IP и IP проверяемого сайта

- В коде, структурах, логах, UI и тестах использовать разные имена/типы для doh_endpoint_ips и probe_target_ips; не использовать неоднозначное общее поле ips.
- DNS endpoint hostname разрешать независимым путём от проверок доменов, с защитой от рекурсии через собственный listener.
- Для HTTPS-запроса к DoH сохранять исходный URL hostname, SNI, проверку сертификата и HTTP Host. При соединении с закреплённым IP hostname остаётся TLS/HTTP-идентичностью запроса.
- Не отключать проверку TLS-сертификата и не подменять URL на IP-литерал.
- При временной ошибке разрешения endpoint hostname не затирать последнюю рабочую пару hostname/IP до безопасного решения контроллера; учитывать возраст endpoint IP.

### 14.3. Безопасность сетевых проверок

- Валидировать DoH URL: допустимые схемы, hostname, порт и путь; запрещать неожиданные схемы, userinfo и некорректные URL.
- Защититься от SSRF: проверять endpoint и probe-адреса, блокировать loopback, link-local, multicast, unspecified и прочие недопустимые диапазоны, кроме явно согласованных исключений.
- Не следовать HTTP redirect на произвольный hostname/IP без повторной валидации каждого перехода; предпочтительно запретить redirects для probe либо ограничить их строгой политикой.
- Ограничить DNS, TCP connect, TLS handshake и HTTP timeouts; ограничить размер тела ответа, число IP на домен и общий объём параллельных запросов.
- Не передавать API-ключи и секреты в URL, диагностические сообщения или обычные логи; очищать чувствительные заголовки и параметры из ошибок.
- Не выполнять произвольный URL из тестового файла без валидации домена, адреса и пути.

### 14.4. DNS корректность и совместимость

- Нормализовать QNAME единым helper: lowercase, удаление завершающей точки для ключа, корректная IDNA-обработка и отказ от некорректных имён.
- A и AAAA обрабатывать строго по типу запроса. При отсутствии endpoint IP нужного семейства возвращать NODATA с корректными SOA/TTL; не подменять ответ адресом другого семейства.
- Явно определить безопасное поведение для HTTPS/SVCB, CNAME, ANY, DNSSEC/DO, EDNS0 и TCP DNS. Не возвращать синтетическую запись другого типа.
- Не менять контракт DNS Gateway для QNAME вне Auto Hosts и для всех запросов при выключенной функции.
- Проверить приоритет: ручной local_hosts → Auto Hosts (если включён и есть точное совпадение) → существующий DNS Gateway.
- Проверить пустой набор endpoint IP, пустой Auto Hosts, malformed DNS packet, неизвестный QTYPE и отказ хранилища.

### 14.5. Контроллер, планирование и защита от флаппинга

- Только один контроллер меняет активный сервер и публикует Auto Hosts. Защитить от второго цикла, повторного старта scheduler и одновременного ручного запуска.
- Использовать bounded worker pool и ограниченную очередь; не запускать неограниченные goroutine/запросы при большом списке серверов или доменов.
- Задать отдельные connect/read/overall timeouts, интервалы, jitter и backoff; не допускать шквала запросов ко всем серверам после рестарта.
- Учитывать cooldown/minimum hold, порог повторных неудач и сохранение текущего сервера при равных оценках. Сбой одного домена не должен сам по себе переключать сервер или удалять весь список.
- Выбор сервера и публикация доменов должны использовать одну версию probe results; устаревший результат не должен перезаписывать более новый.
- Ручной запуск проверки не обходит лимиты, не создаёт второй controller и не меняет сервер вне общей процедуры принятия решения.

### 14.6. Stale/grace, перезапуск и устойчивость хранения

- Разделить параметры: период проверки, timeout, срок свежести результата, grace последнего успеха и максимальный возраст endpoint IP. Не смешивать их с DNS TTL.
- Grace отсчитывается от timestamp последнего успешного probe для пары «активный DoH-сервер × домен». Неуспешные проверки не сдвигают timestamp и не продлевают grace.
- Успешный повторный probe до истечения grace обновляет timestamp последнего успеха и начинает новый срок grace.
- Удалять домен из опубликованного Auto Hosts только после истечения явно заданного grace без нового успеха; единичная ошибка, timeout или временная недоступность resolver не удаляют последнюю успешную запись.
- При переключении активного DoH-сервера нельзя переносить/продлевать срок домена результатами старого сервера: публикация строится по свежим результатам нового активного сервера, с учётом явно заданной политики валидности результатов.
- В Web UI раздельно показывать период проверки и grace, timestamp последнего успеха и оставшееся время хранения; не маскировать бессрочное удержание постоянными неудачными retry.
- При старте загрузить и валидировать сохранённое состояние; не публиковать его до проверки версии схемы, целостности и допустимых значений.
- Записывать файлы через временный файл в том же каталоге, fsync (где применимо), атомарный rename и безопасные права доступа.
- Предусмотреть версию схемы, резервное восстановление и безопасное поведение при повреждённом файле.
- Миграция с 2.2.1 должна быть additive: Auto Hosts по умолчанию OFF; старые файлы и записи tst-domen.txt не переинтерпретируются молча; пользовательские настройки не удаляются и не перезаписываются.
- Лимиты количества доменов, серверов, результатов и размера файлов проверяются при чтении и записи.

### 14.7. Наблюдаемость и управление

- Показывать раздельно активный DoH server ID/URL, endpoint IPv4/IPv6, число доменов, время последнего цикла, число успешных/неуспешных пар и причину выбора сервера.
- Для каждой пары показывать статус, timestamp, длительность и нормализованную причину ошибки; IP сайта помечать как временную probe-цель, не endpoint IP.
- Предусмотреть ротацию и ограничение объёма логов; не записывать без необходимости полный поток пользовательских DNS-запросов.
- UI показывает состояние функции, число опубликованных записей, срок их действия и причину удержания в grace. Ошибка конфигурации не должна незаметно ломать старый DNS Gateway.

### 14.8. Обязательная регрессионная матрица перед релизом

1. Обновление с 2.2.1 без новых полей/файлов: сервис запускается, старые настройки и списки не теряются, Auto Hosts выключен.
2. Auto Hosts OFF: DNS-ответы, upstream selection, cache, hot reload и ручной local_hosts ведут себя как до обновления.
3. Auto Hosts ON: публикуются только домены с актуальным успехом через активный сервер; частичный успех восьми доменов разрешён.
4. Переключение сервера: endpoint IP и список доменов меняются одним snapshot; запросы не видят смешанное состояние.
5. Сбой нового сервера/проверок: сохраняется last-known-good в пределах grace; нет пустой публикации и циклического переключения.
6. Перезапуск во время проверки и записи: нет повреждения состояния, зависания DNS listener или потери последней рабочей базы.
7. IPv4-only, IPv6-only, dual-stack и смена endpoint IP; корректные A/AAAA и NODATA.
8. Параллельные DNS-запросы, ручная проверка, hot reload и переключение не создают гонок и не блокируют DNS listener.
9. TLS hostname/SNI/Host и сертификат корректны при соединении с закреплённым endpoint IP; отрицательные тесты SSRF, redirect и timeout проходят.
10. Rollback на 2.2.1 не требует понимания новых файлов и не повреждает исходные конфиги.

Релиз Auto Hosts не считать готовым только по успешной сборке. Обязательны регрессионные тесты на конфигурации 2.2.1, интеграционные DNS/DoH проверки, аварийное восстановление и подтверждение, что выключенная функция не меняет прежнее поведение.


## 15. Производительность и задержка DNS-резолва

Цель: Auto Hosts не должен заметно увеличивать задержку DNS-ответа клиенту. Для доменов, опубликованных в Auto Hosts, ответ должен формироваться локально из готового состояния в памяти; для остальных доменов сохраняется прежний DNS Gateway pipeline.

### 15.1. Требования к критическому пути DNS

- DNS handler использует только заранее подготовленный неизменяемый snapshot (или эквивалентную безопасную read-copy-update схему). Обновление snapshot выполняется атомарной заменой; запрос не должен видеть частично обновлённое состояние.
- Обработка DNS-запроса не выполняет HTTP/DoH-запросы, TCP/TLS-проверки, разрешение endpoint hostname, дисковый I/O, ожидание фоновых задач или запуск/инициацию переключения сервера.
- Не удерживать mutex/RWMutex в течение сетевых операций, проверок, сериализации больших структур или записи состояния. Чтение snapshot должно быть коротким и не зависеть от длительности фоновых probe.
- Не выполнять синхронную запись probe results, Auto Hosts или конфигурации из DNS handler.
- Для QNAME вне Auto Hosts и при Auto Hosts OFF сохранять прежний путь обработки и его семантику; не добавлять лишние lookup/lock/копирования без необходимости.
- DNS-ответ для Auto Hosts строить из endpoint IP и политики QTYPE в snapshot. Отсутствие адреса нужного семейства обрабатывается как NODATA без сетевого fallback в критическом пути.
- Кэширование и TTL не должны приводить к выдаче endpoint IP после истечения допустимого состояния или после публикации нового snapshot; согласовать TTL с интервалом обновления и grace.
- Ошибка фонового контроллера или хранилища не должна блокировать DNS listener. Сохранять last-known-good snapshot в пределах определённой политики безопасности и срока годности endpoint IP.

### 15.2. Фоновая работа и конкуренция

- Все сетевые проверки, разрешение DoH endpoint hostname, выбор сервера и подготовка нового Auto Hosts выполняются вне DNS handler ограниченным worker pool.
- Ограничить очередь и параллелизм; объединять дублирующиеся проверки одной пары «сервер × домен», применять timeout, backoff и jitter.
- Публиковать согласованный snapshot активного сервера, endpoint IPv4/IPv6 и Auto Hosts одной атомарной операцией.
- Проверить отсутствие гонок между плановым циклом, ручным запуском, hot reload, перезапуском и сменой активного сервера.
- Нагрузка от фоновых проверок не должна приводить к starvation DNS handler, исчерпанию соединений/дескрипторов или неконтролируемому росту памяти.

### 15.3. Измерения и критерии приёмки

До релиза выполнить сравнение базовой версии 2.2.1 и реализации Auto Hosts на одинаковом окружении и наборе запросов. Измерять отдельно:
- холодные запросы (без прогретого DNS cache);
- повторные запросы (с прогретым cache);
- Auto Hosts OFF;
- Auto Hosts ON для домена, присутствующего в списке;
- Auto Hosts ON для домена, отсутствующего в списке;
- обычный DNS Gateway/DoH путь и локальный ответ Auto Hosts.

Для каждого сценария собрать как минимум p50, p95 и p99 latency, throughput (QPS), долю ошибок/timeouts и потребление CPU/RAM. Отдельно измерить задержку DNS handler при одновременном выполнении фоновых probe, переключении активного сервера, hot reload и атомарной публикации snapshot.

Критерии:
- Auto Hosts OFF: отсутствие статистически значимой регрессии относительно 2.2.1; целевой бюджет дополнительной задержки DNS handler — 0 мс за счёт отсутствия нового синхронного этапа.
- Auto Hosts ON, домен в списке: ответ формируется локально из snapshot; не должно быть сетевого ожидания в DNS handler. Зафиксировать p50/p95/p99 и сравнить с локальным baseline.
- Auto Hosts ON, домен вне списка: поведение и задержка соответствуют обычному DNS Gateway пути; не должно быть дополнительной проверки доступности на каждый QNAME.
- Фоновые probe и переключение не должны вызывать зависаний listener, всплесков p99, потери запросов или ошибок из-за блокировок. Установить и документировать допустимый regression budget по p95/p99 на целевом VPS после получения baseline-измерений; не заявлять численные миллисекунды до измерения.
- Провести нагрузочный и soak-тест с параллельными клиентскими запросами и фоновыми циклами; проверить стабильность p95/p99 и отсутствие утечек ресурсов.

Результаты benchmark (окружение, версия, параметры нагрузки, числа p50/p95/p99, QPS, ошибки и CPU/RAM) приложить к PR реализации. Сборка без benchmark и проверок конкурентного доступа не является достаточным подтверждением производительности.

# Auto Hosts — архитектурный план

**Статус:** согласованная концепция; реализация не входит в этот документальный этап.  
**Базовая версия проекта:** 2.2.1  
**Целевая ветка:** `feature/auto-hosts-design`

## 1. Цель и модель данных

Добавить в DoH DNS Gateway необязательную функцию Auto Hosts. Она определяет, какой настроенный Smart DNS/DoH-upstream подходит для конкретного домена, и запоминает эту привязку.

**Auto Hosts — не обычный hosts-файл.** Запись вида «адрес DoH-сервера + домен» означает, что для данного домена следует использовать конкретный DNS-upstream. Адрес DoH-сервера никогда не возвращается клиенту как A/AAAA-адрес запрошенного сайта.

При DNS-запросе клиента плагин отправляет исходный QNAME на выбранный DoH-upstream, получает от него реальные A/AAAA-ответы сайта и возвращает их клиенту. При первом запросе плагин подбирает подходящий upstream проверкой доступности полученных адресов с исходным доменом в TLS SNI и HTTP Host. При последующих запросах использует сохранённую привязку и повторно проверяет её по расписанию или при признаках отказа.

Поскольку текущая конфигурация содержит DoH URL, а не обязательно стабильный IP DNS-резолвера, основной идентификатор записи — ID настроенного DoH-сервера (ссылка на запись в `doh-servers.txt`). IP адреса endpoint могут сохраняться как диагностическая информация, но не заменяют URL/ID: для HTTPS важны hostname, TLS SNI, сертификат и HTTP Host.

## 2. Принципы совместимости

- Auto Hosts — отдельная опция, выключенная по умолчанию.
- При выключенной опции DNS Gateway работает как до появления функции: тот же выбор upstream, fallback, кэш и ручной `local_hosts`.
- Не изменять клиентские правила маршрутизации, Xray DNS integration и исходники LucX-UI.
- Не менять основной алгоритм выбора DoH-upstream для обычного DNS Gateway.
- Проверочные и пользовательские запросы Auto Hosts отправляются напрямую к выбранному DoH endpoint и не должны рекурсивно попадать в собственный DNS listener.
- Ручные записи `local_hosts` и таблица Auto Hosts хранятся раздельно. Ручные записи имеют приоритет и по-прежнему возвращают заданные вручную IP.
- Выключение Auto Hosts останавливает применение динамических привязок, но не обязано удалять их сохранённую базу; повторное включение может использовать её после проверки актуальности.

## 3. Предварительная квалификация DoH: развитие tst-domen.txt

Существующий `tst-domen.txt` развивается из простого списка health-check в набор контрольных сценариев для предварительной проверки каждого настроенного DoH-сервера.

Для каждой пары «DoH-upstream × контрольный домен»:

1. Отправить DNS-запросы A и AAAA (с учётом настроенных типов и параметров проверки) непосредственно выбранному DoH endpoint.
2. Получить все возвращённые адреса, а не только первый.
3. Проверить каждый IP по TCP/TLS с исходным контрольным доменом в SNI и HTTP Host; HTTP path, ожидаемый статус и дополнительные критерии задаются контрольной записью.
4. Сохранить результат проверки по паре «DoH-upstream × контрольный домен» и по каждому проверенному IP/семейству.
5. На основании результатов сформировать приоритетный пул DoH-серверов для Auto Hosts.

Результат предварительной проверки — приоритет, а не жёсткий запрет. Успех на контрольных доменах не гарантирует пригодность сервера для любого пользовательского домена. Если приоритетный пул не подходит для конкретного домена, Auto Hosts может проверить остальные настроенные DoH-upstream.

Формат и миграция существующего `tst-domen.txt` должны быть обратно совместимыми: старые записи продолжают работать в текущем health-check режиме. Расширение формата и семантики согласовать до реализации; не менять существующие поля молча.

## 4. Подбор и применение Auto Hosts

### Первый запрос для домена

1. Получить QNAME и QTYPE пользовательского DNS-запроса.
2. Проверить ручной `local_hosts`; ручная запись имеет приоритет.
3. Если Auto Hosts выключен — продолжить старый путь обработки без изменений.
4. Проверить таблицу Auto Hosts на наличие действующей привязки для домена.
5. Если привязки нет, проверить DoH-upstream в порядке приоритета, сформированном предварительной квалификацией; затем при необходимости проверить остальные настроенные серверы.
6. Для каждого DoH-upstream отправить исходный QNAME с соответствующим DNS-типом и получить его фактический DNS-ответ.
7. Проверить все полученные A/AAAA IP-кандидаты с исходным QNAME в TLS SNI и HTTP Host по применимым контрольным критериям.
8. Выбрать подходящий DoH-upstream и сохранить привязку «домен → DoH server ID», включая статус, время проверки и диагностические сведения.
9. Получить DNS-ответ для исходного запроса от выбранного DoH-upstream и вернуть клиенту именно его фактические DNS-данные. Не подменять их IP-адресом самого DoH-сервера.

### Последующие запросы

- Для домена с действующей привязкой отправлять DNS-запросы на сохранённый DoH-upstream; клиенту возвращать актуальный ответ этого резолвера.
- Не выполнять полный подбор и сетевую проверку на каждом DNS-запросе. Повторная квалификация выполняется по интервалу/сроку действия или при признаках отказа.
- Если сохранённый upstream продолжает проходить проверку, не менять привязку только потому, что другой сервер тоже подходит.
- Если upstream перестал подходить, выполнить повторный подбор среди остальных серверов и обновить привязку после успешного результата.
- При временной недоступности всех DoH-серверов не удалять последнюю рабочую привязку. Использовать её в пределах настроенного stale/grace периода, затем перейти к резервному поведению текущего DNS Gateway.
- Если выбранный DoH-upstream вернул валидный DNS-ответ, но конкретный IP-адрес из ответа не прошёл проверку, не считать такой IP подтверждённым только на основании успешного DNS-запроса. Политика обработки смешанного набора (часть IP прошла проверку) должна быть определена при реализации; нельзя молча отбрасывать рабочие ответы без согласованного правила.

### DNS-типы и ответы

- Поддерживать A и AAAA и корректно передавать исходный QTYPE выбранному DoH-upstream.
- Не сохранять IP сайта как постоянную hosts-запись: адреса сайта могут меняться, а Smart DNS может возвращать разные ответы в зависимости от времени и запроса.
- Не возвращать IP DoH endpoint в качестве адреса сайта.
- Не смешивать ответы A и AAAA.
- Сохранять семантику DNS-ответа выбранного DoH-upstream, включая отрицательные ответы и TTL, с учётом обычного DNS-кэша и политики Auto Hosts.
- Если выбранный upstream не отвечает или возвращает непригодный результат, применять согласованный fallback, не зацикливая запрос через собственный listener.

## 5. Хранилище и приоритеты

- Ручной `local_hosts` остаётся отдельным источником и имеет приоритет.
- Auto Hosts хранится отдельно в каталоге `$LUCX_PLUGIN_DATA`, с атомарной записью/заменой файла.
- Основная динамическая запись содержит: нормализованный домен, ID выбранного DoH-upstream, время последнего успешного подтверждения, время следующей проверки, срок stale/grace и диагностический статус.
- Дополнительно можно хранить историю/результаты квалификации по другим DoH-upstream и контрольным IP. Эти сведения диагностические и не превращаются в DNS A/AAAA-записи для клиента.
- IP адреса DoH endpoint, если сохраняются, являются атрибутами endpoint для диагностики, а не значением ответа домена.
- Сбой проверки не должен приводить к потере последней рабочей привязки.
- Параллельные запросы одного домена объединяются в одну операцию подбора (singleflight/coalescing).
- Предусмотреть лимит размера базы и очистку давно неиспользуемых/просроченных записей.

## 6. Проверка IP и ограничения результата

Проверка должна использовать IP из DNS-ответа выбранного Smart DNS как адрес назначения, но исходное имя сайта как TLS SNI и HTTP Host. Нельзя проверять только DNS-ответ или делать HTTP-запрос к IP без исходного имени.

Успешная проверка означает сетевую/HTTP-доступность по настроенным критериям, но не гарантирует полноценную работу авторизации, приложения или всех API-методов. Проверочные URL, ожидаемые статусы и дополнительные признаки отказа задаются контрольными сценариями.

Проверка выполняется с VPS. Она подтверждает достижимость адреса с VPS, но не является абсолютной гарантией доступности с клиентского устройства.

## 7. Wildcard

Wildcard нельзя трактовать как один заранее выбранный DoH-upstream с фиксированным IP для всех поддоменов. Разные поддомены могут иметь разные DNS-ответы и требования к Smart DNS.

Если поддержка wildcard будет включена, wildcard-правило должно задавать политику подбора для фактического QNAME: при первом запросе конкретного поддомена выполнить разрешение и проверку для полного имени, затем сохранить отдельную привязку для этого полного имени. Семантику bare domain и приоритет точного совпадения необходимо определить до реализации.

## 8. Управление в Web UI

Добавить отдельный раздел Auto Hosts, не смешивая его с существующим редактором `tst-domen.txt` и ручным `local_hosts`.

Предусмотреть:
- переключатель включения/выключения (по умолчанию выключен);
- интервал повторной квалификации выбранного DoH-upstream;
- таймаут и критерии проверки IP;
- срок сохранения последней рабочей привязки (stale/grace);
- лимит динамической базы;
- таблицу доменов с выбранным DoH server ID/endpoint, статусом и временем проверки;
- просмотр результатов предварительной квалификации и диагностических IP;
- ручную очистку динамической базы.

В UI необходимо явно различать IP DoH endpoint и IP сайта из DNS-ответа: ни один адрес endpoint не должен выглядеть как A/AAAA-ответ домена. Точные значения по умолчанию и окончательный набор параметров определить при реализации после проверки существующей конфигурационной модели.

## 9. Этапы реализации

1. **Инвентаризация текущего кода:** DNS pipeline, DoH client, health-check parser/runner, local_hosts, cache, hot reload, Web UI API и редакторы.
2. **Расширение контрольных проверок:** обратная совместимость `tst-domen.txt`, запрос A/AAAA через каждый DoH отдельно, проверка всех IP с SNI/Host, результаты по каждому upstream.
3. **Приоритетный пул:** публикация результатов предварительной квалификации для Auto Hosts без изменения основного выбора upstream.
4. **Движок Auto Hosts:** отдельная опция, таблица домен → DoH server ID, хранилище, конкурентная дедупликация, периодическая повторная квалификация, stale/grace и атомарная запись.
5. **DNS integration внутри плагина:** приоритет ручного `local_hosts`, затем Auto Hosts (запрос исходного QNAME к выбранному DoH и возврат его фактического ответа), затем прежний DNS Gateway fallback.
6. **Web UI:** настройки, статус предварительной квалификации и таблица динамических привязок.
7. **Тестирование:** unit/integration tests для DoH, A/AAAA, нескольких IP в ответе, SNI/Host, ошибок, fallback, hot reload, параллельных запросов, выключенного режима и сохранения старого поведения. Отдельно проверить, что IP DoH endpoint никогда не возвращается как IP запрошенного домена.
8. **Документация и выпуск:** README, changelog, примеры конфигурации, manifest/version и CI.

## 10. Критерии приёмки

- При выключенном Auto Hosts старое поведение подтверждено регрессионными тестами.
- Старые записи `tst-domen.txt` продолжают разбираться без изменения смысла.
- Предварительная проверка обращается к каждому DoH endpoint отдельно и проверяет все полученные IP с исходным SNI/Host.
- Auto Hosts хранит привязку домена к DoH-upstream, а не статические IP сайта в hosts.
- DNS-запрос домена с Auto Hosts направляется на выбранный DoH-upstream; клиент получает фактический DNS-ответ этого upstream.
- IP самого DoH endpoint никогда не подставляется в A/AAAA-ответ сайта.
- Рабочая привязка не меняется без необходимости; временная ошибка не стирает last-known-good.
- Одновременные запросы одного домена не запускают дублирующий подбор.
- Ручной `local_hosts` имеет приоритет и не перезаписывается.
- Изменения не требуют модификации LucX-UI или клиентских правил.
- Все новые настройки и файлы находятся в `$LUCX_PLUGIN_DATA`; запись выполняется безопасно и атомарно.

## 11. Вне объёма

- Изменение исходников LucX-UI.
- Изменение клиентских Xray/sing-box routing rules.
- Реализация полноценного Smart DNS Rule Engine или профилей маршрутизации по QNAME.
- Подмена FakeDNS.
- Автоматическая публикация/изменение конфигурации панели.
- Гарантия доступности приложения только на основании TCP/TLS/HTTP проверки.

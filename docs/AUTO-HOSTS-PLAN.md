# Auto Hosts — архитектурный план

**Статус:** согласованная концепция; реализация не входит в этот документальный этап.  
**Базовая версия проекта:** 2.2.1  
**Целевая ветка:** `feature/auto-hosts-design`

## 1. Назначение и ключевая семантика

Добавить в DoH DNS Gateway необязательную функцию Auto Hosts. Auto Hosts хранит только нормализованные доменные имена, которые успешно проверены через выбранный активный Smart DNS/DoH-сервер. IP активного DoH endpoint хранится отдельно в состоянии Active Smart DNS.

При DNS-запросе домена из Auto Hosts плагин возвращает IP активного DoH endpoint соответствующего семейства (A — IPv4, AAAA — IPv6). IP сайта, полученный при проверке через DoH, используется только для TCP/TLS/HTTP-проверки и никогда не записывается в Auto Hosts или в DNS-ответ клиенту.

**Логическая модель данных:**

- `auto_hosts`: множество доменных имён без IP-значений;
- `active_smart_dns`: ID выбранного DoH-сервера, его исходный URL/hostname и отдельно разрешённые IPv4/IPv6 endpoint;
- `probe_results`: результаты проверок для каждой пары «DoH-сервер × домен», включая временный IP сайта, статус, время и диагностику.

IP endpoint должен разрешаться отдельно от IP сайта. Для HTTPS-запросов к DoH сохраняются исходные URL hostname, TLS SNI, проверка сертификата и HTTP Host.

## 2. Алгоритм заполнения Auto Hosts

Список из восьми доменов заменяет прежние 25 health-check доменов. Каждый домен проверяется отдельно через каждый настроенный DoH endpoint; успешность одного домена не зависит от результатов остальных:

1. Фоновый монитор отправляет DNS-запрос контрольного домена непосредственно через проверяемый DoH endpoint, не используя локальный DNS listener плагина.
2. Получает IP сайта из DNS-ответа. Этот IP — временная цель проверки, он не является IP DoH endpoint.
3. Проверяет доступность сайта по TCP/TLS/HTTP с исходным доменом в SNI и HTTP Host; URL/path, ожидаемый статус и дополнительные критерии задаются тестовой записью.
4. Сохраняет результат отдельно для пары «DoH-сервер × домен». Успешная проверка домена через сервер A не означает, что этот домен доступен через сервер B.
5. Если домен успешно проверен через текущий активный сервер, его имя добавляется в Auto Hosts. Если проверка неуспешна, домен не добавляется (или сохраняется до окончания stale/grace, если ранее был подтверждён).
6. Не требуется, чтобы один DoH-сервер успешно прошёл все восемь доменов. Частичные результаты допустимы и ожидаемы.

IP самого DoH endpoint разрешается отдельно по hostname URL и хранится в `active_smart_dns`; он не копируется в каждую запись Auto Hosts. При HTTPS-проверках сохраняются исходные hostname URL, TLS SNI, сертификат и HTTP Host.

## 3. DNS-поведение Auto Hosts

При получении клиентского DNS-запроса:

1. Проверить ручной `local_hosts`; ручная запись имеет наивысший приоритет.
2. Если Auto Hosts выключен, продолжить существующий DNS Gateway pipeline без изменений.
3. Если Auto Hosts включён и домен присутствует в Auto Hosts, вернуть IP единственного активного DoH endpoint из отдельного состояния `active_smart_dns`. Все домены Auto Hosts в один момент времени используют один и тот же активный endpoint.
4. Если домена нет в Auto Hosts, использовать прежнее поведение DNS Gateway; заполнение Auto Hosts выполняется отдельным фоновым механизмом.
5. Для A возвращать IPv4 активного endpoint, для AAAA — IPv6. Если адреса соответствующего семейства нет, отвечать NODATA; не подменять AAAA-ответ IPv4-адресом.

Таким образом, Auto Hosts — именно динамический hosts-подобный список DNS-ответов, а не таблица выбора upstream для последующего разрешения пользовательского QNAME.

## 4. tst-domen.txt и предварительные проверки

Существующий `tst-domen.txt` развивается в список контрольных доменов и сценариев проверки пригодности DoH-серверов для этих доменов.

Базовый набор доменов берётся из проекта-примера HB AI (`Probe.Host`) без самовольного расширения:

| Домен | Назначение |
|---|---|
| `chatgpt.com` | ChatGPT |
| `claude.ai` | Claude |
| `gemini.google.com` | Gemini |
| `elevenlabs.io` | ElevenLabs |
| `grok.com` | Grok |
| `www.perplexity.ai` | Perplexity |
| `notebooklm.google.com` | NotebookLM |
| `aistudio.google.com` | Google AI Studio |

Именно этот набор из восьми доменов заменяет прежний список из 25 health-check доменов. Каждый домен проверяется независимо через каждый настроенный DoH-сервер; успешный результат одной проверки не требует успеха остальных семи. Список остаётся редактируемым через `tst-domen.txt`/Web UI; новые домены добавляются явно.

Для каждой пары «DoH-сервер × контрольный домен»:

- отправить DNS-запрос A/AAAA непосредственно на соответствующий DoH endpoint;
- получить все IP сайта из ответа;
- проверить IP сайта по TCP/TLS с исходными SNI и HTTP Host, URL/path, ожидаемым HTTP-статусом и дополнительными условиями;
- если конкретный домен успешно прошёл проверку через конкретный DoH endpoint, сохранить успешный результат этой пары;
- если конкретный домен успешно проверен через текущий активный endpoint, добавить/обновить только имя этого домена в Auto Hosts;
- IP сайта, полученные через DoH, использовать только в процессе проверки и не помещать в Auto Hosts;
- не требовать полного успеха всех восьми доменов для включения отдельного домена.

Предварительная проверка не является гарантией доступности для каждого пользователя: она выполняется с VPS и подтверждает доступность с VPS. Контрольный список не должен превращаться в жёсткий запрет для остальных доменов, если позднее будет добавлена проверка по запросу или расширение набора тестов.

Формат и миграция существующего `tst-domen.txt` должны быть обратно совместимыми. Старые записи продолжают работать в текущем health-check режиме; расширение формата и семантики согласовать до реализации, не меняя существующие поля молча.

## 5. Обновление и сохранность записей

- Не проверять все домены и все серверы на каждом DNS-запросе.
- Выполнять проверки по расписанию, при ручном запуске или по явно определённому событию обновления.
- Объединять параллельные проверки одной пары «домен × DoH-сервер» в одну операцию.
- Успешная повторная проверка обновляет время подтверждения записи.
- Временная ошибка не удаляет последнюю успешную запись. Предусмотреть срок stale/grace и отдельную политику окончательного устаревания.
- Результаты проверок всех DoH-серверов хранить раздельно по доменам. Смена активного сервера требует пересобрать Auto Hosts по успешным и ещё действительным результатам проверок именно нового активного сервера.
- Предусмотреть лимит размера списка, атомарную запись файла и очистку окончательно устаревших записей.

## 6. Хранилище, приоритеты и форматы

- Ручной `local_hosts` и Auto Hosts — разные хранилища.
- Ручной `local_hosts` всегда имеет приоритет над Auto Hosts.
- Auto Hosts хранится отдельно в `$LUCX_PLUGIN_DATA`.
- Auto Hosts хранит только нормализованные доменные имена, без IP-адресов.
- `active_smart_dns` отдельно хранит ID активного DoH-сервера, исходный URL/hostname и разрешённые IP endpoint (IPv4/IPv6).
- `probe_results` отдельно хранит состояние каждой пары «DoH-сервер × домен», время последней проверки, временные IP сайта и диагностику.
- Не сохранять IP сайта, полученный из DNS-ответа проверочного DoH-запроса, в Auto Hosts или в качестве IP активного endpoint.
- Если один DoH URL разрешается в несколько IP, хранить все допустимые адреса отдельно в состоянии endpoint; не терять hostname URL, необходимый для корректного HTTPS/SNI.
- В каждый момент времени активен один выбранный DoH endpoint; Auto Hosts не содержит доменно-зависимых пулов серверных IP.
- Запись и замена файла должны быть атомарными, чтобы сбой процесса не повреждал последнюю рабочую базу.

## 7. DNS-типы и ограничения

- Определить поведение A и AAAA отдельно: IP-адрес DoH endpoint может быть IPv4 и/или IPv6. Возвращать только адреса соответствующего семейства.
- Для типов, не поддерживаемых hosts-подобной записью (например, HTTPS/SVCB), сохранить согласованное безопасное поведение существующего DNS Gateway; не подменять их произвольными A/AAAA-ответами.
- Нормализовать домены, корректно обрабатывать завершающую точку и регистр.
- На первом этапе поддерживать точные доменные имена. Wildcard требует отдельного определения семантики и приоритетов.
- TTL Auto Hosts должен быть ограниченным и согласованным с периодом обновления; не выдавать бесконечный TTL.
- Не допускать рекурсивного обращения проверочного DoH-запроса к собственному DNS listener.

## 8. Wildcard

Wildcard не включать автоматически в первый этап. До его реализации определить:
- область действия правила и обработку apex-домена;
- приоритет точного совпадения над wildcard;
- распространяется ли IP DoH endpoint на все поддомены или для каждого фактического QNAME требуется отдельная проверка;
- как обновлять и удалять wildcard-записи без потери последней рабочей конфигурации.

## 9. Управление в Web UI

Добавить отдельный раздел Auto Hosts, не смешивая его с ручным `local_hosts` и редактором `tst-domen.txt`.

Предусмотреть:
- переключатель Auto Hosts (по умолчанию выключен);
- интервал проверок, таймауты и критерии доступности;
- срок сохранения последней успешной записи (stale/grace);
- лимит размера списка;
- таблицу доменов, включённых в Auto Hosts;
- отдельное отображение активного DoH-сервера и его IPv4/IPv6 endpoint;
- таблицу результатов проверок по парам «DoH-сервер × домен»;
- отображение времени последней проверки и состояния записи;
- просмотр диагностических результатов, включая IP сайта, использованные только для проверки;
- ручной запуск проверок и очистку динамического списка.

В UI и диагностике явно разделять три сущности: IP DoH endpoint, IP сайта из ответа DoH и IP, возвращаемый клиенту из Auto Hosts. В Auto Hosts и в DNS-ответе для домена используется именно IP DoH endpoint.

## 10. Совместимость и границы изменений

- Auto Hosts — отдельная опция, выключенная по умолчанию.
- При выключенной опции существующее поведение DNS Gateway не меняется.
- Не менять текущий алгоритм выбора основного DoH-upstream для обычных DNS-запросов.
- Не менять клиентские правила маршрутизации, Xray DNS integration и исходники LucX-UI.
- Проверочные запросы отправлять непосредственно к DoH endpoint, не через собственный DNS listener.
- Все новые настройки и файлы размещать в `$LUCX_PLUGIN_DATA`.
- Реализация и Web UI остаются внутри плагина.

## 11. Этапы реализации

1. Инвентаризировать DNS pipeline, DoH client, health-check parser/runner, `local_hosts`, cache, hot reload и Web UI API.
2. Заменить прежние 25 health-check доменов единым списком из восьми доменов; проверять каждую пару «DoH-сервер × домен» независимо, получать IP сайта и проверять его с исходными SNI/Host.
3. Реализовать отдельные хранилища Auto Hosts (только доменные имена), `probe_results` и `active_smart_dns` (ID/URL и IP endpoint), с атомарным обновлением и stale/grace.
4. Добавить DNS-ответы из Auto Hosts: ручной `local_hosts` приоритетнее; для Auto Hosts возвращать IP единственного активного DoH endpoint, хранящийся отдельно.
5. Реализовать единый фоновый контроллер выбора активного сервера и атомарную публикацию состояния; DNS-запросы не должны запускать проверки или переключение.
6. Добавить настройки и просмотр Auto Hosts в Web UI.
7. Добавить unit/integration tests: успешная/неуспешная проверка каждого из восьми доменов, включение endpoint только при успехе всего набора, идентичность IP-наборов у всех доменов, атомарное обновление без частичных списков, несколько DoH IP, несколько IP сайта, A/AAAA, SNI/Host, TTL, fallback, временный сбой, stale/grace, hot reload, параллельные проверки, выключенный режим и приоритет ручного `local_hosts`.
8. Обновить README, changelog, примеры конфигурации, manifest/version и CI.

## 12. Критерии приёмки

- При выключенном Auto Hosts старое поведение подтверждено регрессионными тестами.
- Проверочный DNS-запрос выполняется непосредственно через проверяемый DoH endpoint.
- IP сайта из DNS-ответа используется только для TCP/TLS/HTTP-проверки с исходными SNI и Host.
- Прежний список из 25 health-check доменов заменён набором из восьми доменов.
- Проверки каждой пары «DoH-сервер × домен» выполняются независимо; успех одного домена не зависит от остальных.
- Auto Hosts содержит только имена доменов, подтверждённо доступных через текущий активный сервер (с учётом stale/grace).
- IP активного DoH endpoint хранится отдельно; запрос любого домена из Auto Hosts получает IP этого единственного endpoint, а не IP сайта.
- Несколько DNS-запросов не могут инициировать конкурирующие переключения активного сервера.
- Временная ошибка проверки не удаляет последнюю успешную запись.
- Ручной `local_hosts` имеет приоритет и не перезаписывается.
- Проверки не зацикливаются через собственный DNS listener.
- Изменения не требуют модификации LucX-UI или клиентских правил.
- Все новые данные хранятся отдельно в `$LUCX_PLUGIN_DATA` и записываются атомарно.

## 13. Вне объёма

- Изменение исходников LucX-UI.
- Изменение клиентских Xray/sing-box routing rules.
- Полноценный Smart DNS Rule Engine или таблица выбора upstream для каждого пользовательского DNS-запроса.
- FakeDNS.
- Автоматическая публикация/изменение конфигурации панели.
- Гарантия доступности приложения только на основании TCP/TLS/HTTP-проверки.

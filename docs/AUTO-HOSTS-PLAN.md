# Auto Hosts — архитектурный план

**Статус:** согласованная концепция; реализация не входит в этот документальный этап.  
**Базовая версия проекта:** 2.2.1  
**Целевая ветка:** `feature/auto-hosts-design`

## 1. Цель

Добавить в DoH DNS Gateway необязательную функцию Auto Hosts. Функция динамически обучает локальную DNS-базу на реальных запросах, которые уже направляются клиентскими правилами в DNS Gateway.

Для домена Auto Hosts получает ответы от настроенных DoH-upstream, проверяет все полученные IPv4/IPv6 адреса с исходным доменом в TLS SNI и HTTP Host, сохраняет все пригодные адреса и возвращает их клиенту. При последующих запросах сохранённые адреса проверяются повторно; пока они работают, запись не меняется. Если они перестают работать, выполняется повторный подбор через другие DoH-upstream.

## 2. Принципы совместимости

- Auto Hosts — отдельная опция, выключенная по умолчанию.
- При выключенной опции DNS Gateway должен работать как до появления функции: тот же выбор upstream, fallback, кэш и ручной `local_hosts`.
- Не изменять клиентские правила маршрутизации, Xray DNS integration и исходники LucX-UI.
- Не менять основной алгоритм выбора DoH-upstream для обычного DNS Gateway.
- Проверочные запросы Auto Hosts выполняются напрямую к DoH endpoint и не должны рекурсивно попадать в собственный DNS listener.
- Ручные записи `local_hosts` и автоматически накопленные записи хранятся раздельно. Ручные записи имеют приоритет.
- Выключение Auto Hosts останавливает участие динамических записей в DNS-ответах, но не обязано удалять сохранённую базу; повторное включение может использовать её после проверки актуальности.

## 3. Предварительная квалификация DoH: развитие tst-domen.txt

Существующий `tst-domen.txt` развивается из простого списка health-check в список контрольных сценариев для предварительной проверки каждого настроенного DoH-сервера.

Для каждого DoH-upstream и контрольного домена:

1. Отправить DNS-запросы A и AAAA (с учётом настроенных типов/параметров проверки).
2. Получить все возвращённые адреса, а не только первый.
3. Проверить каждый IP по TCP/TLS с исходным доменом в SNI и HTTP Host; HTTP path, ожидаемый статус и дополнительные критерии задаются контрольной записью.
4. Сохранить результат по связке «DoH-upstream × контрольный домен × IP/семейство».
5. Сформировать приоритетный пул DoH-серверов для Auto Hosts.

Результат предварительной проверки — приоритет, а не жёсткий запрет. Успех на контрольных доменах не гарантирует пригодность сервера для любого пользовательского домена. Если приоритетный пул не дал рабочий адрес для конкретного домена, Auto Hosts может проверить остальные настроенные DoH-upstream.

Формат и миграция существующего `tst-domen.txt` должны быть обратно совместимыми: старые записи продолжают работать в текущем health-check режиме. Расширение формата и семантики согласовать до реализации; не менять существующие поля молча.

## 4. Динамический Auto Hosts

### Первый запрос

1. Получить QNAME и QTYPE пользовательского DNS-запроса.
2. Проверить ручной `local_hosts`; ручная запись имеет приоритет.
3. Если Auto Hosts выключен — продолжить старый путь обработки без изменений.
4. Если Auto Hosts включён, проверить динамическую запись для домена.
5. Если записи нет, опросить DoH-upstream: сначала предварительно квалифицированный пул, затем при необходимости остальные настроенные серверы.
6. Для каждого сервера запросить соответствующие A/AAAA и собрать все адреса.
7. Проверить все кандидаты с исходным доменом в SNI/Host и заданными сетевыми/HTTP критериями.
8. Сохранить все прошедшие проверку IPv4 и IPv6, метаданные источника и время проверки.
9. Вернуть клиенту DNS-ответ с проверенными адресами.

### Последующие запросы

- Сначала использовать сохранённые адреса Auto Hosts.
- Проверять сохранённые адреса не на каждом DNS-запросе, а по интервалу/сроку проверки и по признакам отказа, чтобы не добавлять задержку каждому запросу.
- Если адреса остаются рабочими, не менять запись только потому, что другой DoH-сервер предложил другой IP.
- Если часть адресов перестала работать, перепроверить набор и сохранить все подтверждённые рабочие адреса.
- Если все адреса перестали работать, выполнить повторный подбор через DoH и атомарно заменить запись после получения пригодного результата.
- При временной недоступности всех DoH-серверов не уничтожать последнюю рабочую запись: использовать её в пределах настроенного срока stale/grace, затем перейти к резервному поведению текущего DNS Gateway.

### Множество адресов и DNS-типы

- Сохранять все проверенные A и AAAA адреса, а не только первый адрес.
- Не смешивать результаты IPv4 и IPv6.
- Корректно обрабатывать запросы A, AAAA и ответы, содержащие несколько адресов.
- Не возвращать NODATA для семейства только потому, что для него нет Auto Hosts записи, если политика fallback должна позволить обычному upstream ответить на этот тип запроса.
- TTL DNS-ответа должен быть согласован с политикой повторной проверки и сроком хранения записи.

## 5. Хранилище и приоритеты

- Ручной `local_hosts` остаётся отдельным источником и имеет приоритет.
- Auto Hosts хранится отдельно в каталоге `$LUCX_PLUGIN_DATA`, с атомарной записью/заменой файла.
- Для динамической записи хранить: нормализованный домен, все проверенные IPv4/IPv6, DoH source ID, время последнего успеха, время следующей проверки, срок stale/grace и диагностический статус.
- Сбой проверки не должен приводить к потере последнего рабочего набора адресов.
- Параллельные запросы одного домена объединяются в одну операцию подбора (singleflight/coalescing).
- Предусмотреть лимит размера базы и очистку давно неиспользуемых/просроченных записей.

## 6. Проверка IP

Проверка должна использовать IP как адрес назначения, но исходное имя домена как TLS SNI и HTTP Host. Нельзя проверять только DNS-ответ или делать HTTP-запрос к IP без исходного имени.

Успешная проверка означает сетевую/HTTP-доступность по настроенным критериям, но не гарантирует полноценную работу авторизации, приложения или всех API-методов. Проверочные URL, ожидаемые статусы и дополнительные признаки отказа задаются контрольными сценариями.

Нужно учитывать, что проверка выполняется с VPS. Она подтверждает достижимость адреса с VPS, но не является абсолютной гарантией доступности с клиентского устройства.

## 7. Wildcard

Wildcard нельзя трактовать как один заранее проверенный IP для всех поддоменов: разные поддомены могут иметь разные ответы. Если поддержка wildcard будет включена, предпочтительный вариант — wildcard-правило как политика для конкретного QNAME: получать и проверять адреса фактического поддомена при его первом запросе и кэшировать результат отдельно для этого полного имени. Семантику bare domain и приоритет точного совпадения необходимо определить до реализации.

## 8. Управление в Web UI

Добавить отдельный раздел Auto Hosts, не смешивая его с существующим редактором `tst-domen.txt` и ручным `local_hosts`.

Предусмотреть:
- переключатель включения/выключения (по умолчанию выключен);
- интервал повторной проверки;
- таймаут и критерии проверки IP;
- срок сохранения последней рабочей записи (stale/grace);
- лимит динамической базы;
- просмотр доменов, всех IPv4/IPv6, источника DoH, статуса и времени проверки;
- ручную очистку динамической базы;
- видимый статус предварительной квалификации DoH по контрольным доменам.

Точные значения по умолчанию и окончательный набор параметров определить при реализации после проверки существующей конфигурационной модели.

## 9. Этапы реализации

1. **Инвентаризация текущего кода:** DNS pipeline, DoH client, health-check parser/runner, local_hosts, cache, hot reload, Web UI API и редакторы.
2. **Расширение контрольных проверок:** обратная совместимость `tst-domen.txt`, запрос A/AAAA через каждый DoH отдельно, проверка всех IP с SNI/Host, результаты по каждому upstream.
3. **Приоритетный пул:** публикация результатов предварительной квалификации для Auto Hosts без изменения основного выбора upstream.
4. **Движок Auto Hosts:** отдельная опция, хранилище, конкурентная дедупликация запросов, проверка/обновление всех адресов, stale/grace и атомарная запись.
5. **DNS integration внутри плагина:** приоритет ручного `local_hosts`, затем Auto Hosts, затем прежний DNS Gateway fallback; корректные A/AAAA и TTL.
6. **Web UI:** настройки, статус предварительной проверки и таблица динамических записей.
7. **Тестирование:** unit/integration tests для DoH, A/AAAA, нескольких IP, SNI/Host, ошибок, fallback, hot reload, параллельных запросов, выключенного режима и сохранения старого поведения.
8. **Документация и выпуск:** README, changelog, примеры конфигурации, manifest/version и CI.

## 10. Критерии приёмки

- При выключенном Auto Hosts старое поведение подтверждено регрессионными тестами.
- Старые записи `tst-domen.txt` продолжают разбираться без изменения смысла.
- Предварительная проверка обращается к каждому DoH endpoint отдельно и проверяет все полученные IP с исходным SNI/Host.
- Auto Hosts сохраняет и возвращает все проверенные A/AAAA адреса.
- Рабочая запись не меняется без необходимости; временная ошибка не стирает last-known-good.
- Одновременные запросы одного домена не запускают дублирующий подбор.
- Ручной `local_hosts` имеет приоритет и не перезаписывается.
- Изменения не требуют модификации LucX-UI или клиентских правил.
- Все новые настройки и файлы находятся в `$LUCX_PLUGIN_DATA`; запись выполняется безопасно и атомарно.

## 11. Вне объёма

- Изменение исходников LucX-UI.
- Изменение клиентских Xray/sing-box routing rules.
- Реализация полноценного Smart DNS Rule Engine или профилей маршрутизации по QNAME.
- Подмена FakeDNS.
- Автоматическая публикация/изменение конфигурации панели.
- Гарантия доступности приложения только на основании TCP/TLS/HTTP проверки.

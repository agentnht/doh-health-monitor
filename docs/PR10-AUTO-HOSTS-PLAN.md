## Зафиксированный план дальнейшей работы — Auto Hosts 3.0

Продолжаем разработку **только в ветке `feature/auto-hosts-v3`**. Этот комментарий фиксирует актуальную согласованную семантику и дополняет первоначальный план PR #9 там, где уточнились DNS-маршрутизация и динамическое наполнение Auto Hosts.

### 1. Итоговая DNS-логика

Приоритет обработки DNS-запроса:

1. `local_hosts` — наивысший приоритет.
2. Проверка QNAME по выбранным категориям Geosite.
3. Для Geosite HIT:
   - Auto Hosts включён и Emergency OFF не установлен: добавить/обновить QNAME в Auto Hosts и вернуть IP endpoint текущего активного DoH-сервера;
   - Auto Hosts выключен или Emergency OFF включён: отправить запрос в `vps-resolve`.
4. Для Geosite MISS: отправить запрос в `vps-resolve`.

**`vps-resolve` — отдельный DoH upstream Quad9 Secure:** `https://dns.quad9.net/dns-query`. Это фиксированный resolver для указанной ветки, он не участвует в выборе активного Auto Hosts-сервера и не заменяется случайным upstream из общего пула. Реализация должна проверить поддержку HTTP/2: Quad9 отключил HTTP/1.1 для DoH.

### 2. Auto Hosts — единый динамический список

Содержимое Auto Hosts формируется из двух источников:

- восемь фиксированных контрольных доменов: `chatgpt.com`, `claude.ai`, `gemini.google.com`, `elevenlabs.io`, `grok.com`, `www.perplexity.ai`, `notebooklm.google.com`, `aistudio.google.com`;
- пользовательские домены, QNAME которых поступили в DNS-запросах при Geosite HIT и включённом Auto Hosts.

Восемь контрольных доменов одновременно входят в Auto Hosts и используются только для оценки доступности DoH-серверов и выбора активного сервера. Они не являются allowlist пользовательских имён.

Для всех записей действует единый формат и механизм управления:
- нормализация имени до канонического lowercase/FQDN без завершающей точки;
- проверка существования записи до добавления;
- ключ по нормализованному домену и отсутствие дубликатов;
- обновление временных меток существующей записи;
- общий лимит списка и атомарное обновление состояния.

Пользовательский домен не требуется отдельно проверять через все DoH-серверы. Для него достаточно факта DNS-запроса, попавшего в ветку Geosite HIT + Auto Hosts ON.

### 3. Возвращаемый IP

Для любого домена, присутствующего в Auto Hosts, плагин возвращает не IP сайта, а IP endpoint **единственного текущего активного DoH-сервера**:
- A — IPv4 endpoint;
- AAAA — IPv6 endpoint;
- отсутствие адреса нужного семейства — NODATA;
- HTTPS/SVCB — сохранить согласованную текущую политику Auto Hosts.

Endpoint хранится отдельно от доменных записей. Переключение активного сервера атомарно меняет endpoint для всего списка; не требуется индивидуально проверять пользовательские домены или записывать IP в каждую запись.

Если Auto Hosts включён, но нет пригодного/свежего endpoint или запись не удалось безопасно добавить из-за лимита/ошибки хранилища, не выдавать старый или неподтверждённый IP: перейти на `vps-resolve`.

### 4. Время жизни и периодическая очистка Auto Hosts

Сохраняется политика stale/grace из архитектурного PR #9. Это **не периодический полный сброс всего списка**, а регулярная очистка отдельных устаревших записей.

Разделить два основания продления срока:
- для восьми контрольных доменов — последний успешный probe через текущий активный DoH-сервер;
- для пользовательских доменов — последнее фактическое DNS-обращение клиента к домену (LastSeen).

Успешная активность обновляет timestamp и срок хранения. Неуспешные probe не продлевают grace контрольного домена. Повторный DNS-запрос обновляет LastSeen пользовательского домена. Неактивные пользовательские записи удаляются после истечения заданного grace.

Очистка должна:
- выполняться периодически отдельным обслуживающим механизмом;
- не зависеть от успешного завершения очередного probe-цикла;
- удалять просроченные записи из persistence и публикуемого immutable DNS snapshot;
- не удалять актуальные записи;
- работать безопасно при параллельных DNS-запросах, probe, переключении сервера и рестарте.

Период проверки DoH, grace хранения домена и DNS TTL — разные параметры. Существующие стартовые значения PR #10: check interval 5 минут, grace 30 минут, DNS TTL 60 секунд, лимит 64 домена; сохранить их как исходные defaults, если тесты/UX не выявят необходимости уточнить значения.

При смене активного сервера домены не должны теряться только из-за смены ID сервера. Их список остаётся общим, меняется endpoint. Состояние качества активного сервера контролируется отдельно; stale/grace применяется к доменной записи, а freshness — к endpoint IP.

### 5. Контрольные DoH-проверки и выбор сервера

- Каждый настроенный DoH-сервер проверяется по всем восьми контрольным доменам.
- Для каждой пары сервер × контрольный домен сохраняется отдельный результат.
- Проверка: прямой DoH A/AAAA, затем HTTPS к полученному IP с исходными hostname, TLS SNI, Host и проверкой сертификата.
- IP сайта используется только для проверки, не возвращается DNS-клиенту.
- Один фоновый контроллер выбирает активный сервер; сохраняются Auto/Pinned, anti-flap, min-hold, cooldown, Dry Run, Emergency OFF, bounded workers, backoff/jitter.
- Probe domains и динамический список Auto Hosts — разные сущности; циклы проверок не должны затирать пользовательские записи.

### 6. Geosite

- Geosite всегда активен; пользовательского переключателя Enabled не добавлять.
- Читать бинарный `geosite.dat`, который уже загружает панель, в режиме read-only; не менять исходники LucX-UI и не обращаться к закрытому Xray API.
- Предпочтительный стандартный путь: `/usr/local/x-ui/bin/geosite.dat`, вычисляемый от `LUCX_PLUGIN_DATA`; предусмотреть конфигурационный override и диагностику пути/ошибки.
- Загружать только выбранные категории, не материализовать весь файл; поддержать корректную семантику Domain, Full, Substr, Regex.
- Построить immutable index заранее, атомарно публиковать его; при ошибке обновлённого файла сохранять последний рабочий индекс.
- Geosite MISS и HIT при Auto Hosts OFF/Emergency OFF идут в `vps-resolve`.

### 7. Ограничения области работ

- Изменения выполняются только в репозитории плагина и его Web UI.
- Не изменять код LucX-UI.
- Не выполнять работы по Xray routing rules или Integrate/DeIntegrate; сохранить только README-пояснение о необходимости направить клиентский трафик через TProxy inbound Xray, чтобы DNS-перехват вообще происходил.
- Не менять клиентские правила.
- PR #10 остаётся Draft и не сливается до завершения тестов и отдельного VPS gate.

### 8. Исправления текущей реализации PR #10

1. Разделить probe diagnostics и список обслуживаемых доменов.
2. Добавить idempotent add/update QNAME из DNS handler для Geosite HIT + Auto Hosts ON.
3. Добавить LastSeen для пользовательских записей и продление срока по запросам.
4. Сохранять восемь контрольных доменов как системные записи; обновлять их срок только успешным probe активного сервера.
5. Ввести независимый periodic garbage collector, который очищает просроченные записи и публикует новое состояние атомарно.
6. Исправить ApplyFullCycle так, чтобы он не удалял и не перезаписывал актуальные пользовательские записи.
7. Добавить отдельный upstream `vps-resolve` на Quad9 Secure DoH и гарантировать, что перечисленные ветки идут именно через него, а не через общий пул.
8. Реализовать Geosite matcher и включить его в DNS pipeline.
9. Сохранить быстрый DNS critical path: никаких сетевых probe и файлового I/O из обработчика DNS; ограничить lock time и кэшировать/инвалидировать корректно.
10. Обновить Web UI: выбранные Geosite categories, состояние geosite.dat, список Auto Hosts, источник записи, LastSeen/last success, время до expiry, активный сервер и endpoint, состояние cleanup.

### 9. Тесты и приёмка

- Восемь контрольных доменов присутствуют в Auto Hosts, но не ограничивают его состав.
- Новый пользовательский QNAME добавляется на Geosite HIT; повторный запрос не создаёт дубликат и обновляет LastSeen.
- Geosite MISS → Quad9; Geosite HIT + Auto Hosts OFF → Quad9; Geosite HIT + Emergency OFF → Quad9.
- Geosite HIT + Auto Hosts ON → IP текущего активного endpoint.
- Для всех доменов endpoint меняется при переключении сервера.
- Периодическая очистка удаляет пользовательские записи после grace без обращений и контрольные записи после отсутствия успешных проверок; неудачный probe cycle не блокирует cleanup.
- Auto Hosts не переполняется; при достижении лимита запрос безопасно разрешается через Quad9 без синтетического ответа.
- Проверить IPv4/IPv6, NODATA, HTTPS/SVCB, TTL, endpoint freshness, persistence, restart, concurrent DNS/probe/cleanup, race detector, DoH Quad9 HTTP/2.
- Geosite тесты: точное совпадение, поддомены, Full, Substr, Regex, неверный/отсутствующий файл, горячая замена и сохранение старого индекса при ошибке.
- CI и VPS gate обязательны; VPS deployment ещё не считать выполненным до фактической проверки.

### Источники и контекст
- Архитектура stale/grace зафиксирована в PR #9, commit `0ead0da`: успешное подтверждение продлевает срок, временная ошибка не продлевает, после истечения grace запись удаляется.
- История PR #10 просмотрена: 223 коммита. В текущем коде уже есть GracePeriod/ExpiresAt и удаление старых записей при ApplyFullCycle, но нет динамического добавления QNAME из DNS handler, а очистка связана с успешным probe cycle — это требуется исправить.
- Официальный Quad9 Secure DoH endpoint: `https://dns.quad9.net/dns-query`.

**Это план работ, не отчёт о выполненной реализации. На момент фиксации комментария код PR #10 не меняется.**

## Дополнение к обязательному плану: DNS-интеграция и TProxy

Этот раздел является обязательной частью плана PR #10 и уточняет ограничения на работы с Xray.

### A. DNS-маршрутизация: только документация TProxy

Работы по изменению порядка Xray routing rules, Integrate/DeIntegrate и автоматическому добавлению DNS-правил **полностью исключены из объёма реализации PR #10**.

Не менять:
- правила маршрутизации Xray и их порядок;
- существующую логику Integrate/DeIntegrate;
- автоматическое добавление/перестановку DNS routing rules;
- клиентские конфигурации.

В README оставить одно обязательное пояснение (смысл и формулировка должны быть сохранены):

> Одного правила Xray недостаточно, чтобы перехватить DNS-пакеты, проходящие через обычную маршрутизацию Linux. Трафик клиентов, пришедший через туннель, должен быть фактически направлен во входящий TProxy Xray. Только после этого DNS-запросы смогут обрабатываться правилами Xray и передаваться в DNS outbound плагина.

### B. Документация DNS-интеграции в README

README должен описывать взаимодействие компонентов в следующем порядке:

1. Клиент отправляет DNS-запрос через туннель.
2. Трафик попадает во входящий TProxy Xray.
3. Xray routing направляет DNS-трафик в DNS outbound плагина.
4. DNS-прокси анализирует доменное имя и выбирает дальнейший маршрут (Auto Hosts или `vps-resolve` согласно зафиксированной DNS-логике).
5. Ответ возвращается клиенту через исходный сетевой путь.

Это только документирование существующей требуемой схемы. Никаких Xray routing rules или Integrate/DeIntegrate в рамках PR #10 менять не нужно.

### C. DNS-порты — не фиксировать как окончательную архитектуру

Текущие значения портов из конфигурации/версии 2.2.1 не объявлять окончательными архитектурными значениями. README и проектная документация не должны создавать впечатление, что порт DNS listener уже окончательно закреплён.

Автоматический выбор свободного DNS-порта остаётся отдельной открытой инженерной задачей, которую необходимо проработать в рамках плагина:

- определить безопасный алгоритм поиска свободного UDP/TCP порта (пара сокетов должна резервироваться согласованно);
- определить, как выбранный порт сохраняется и восстанавливается после перезапуска;
- определить, как фактически выбранный порт передаётся/объявляется Xray DNS outbound без изменения исходников LucX-UI;
- определить порядок запуска, чтобы плагин не сообщал Xray порт до успешного bind listener;
- обеспечить обработку конфликта порта и повторный выбор без ложного сообщения об успешной интеграции;
- определить, как health checks, Web UI, API, диагностика и Integrate/DeIntegrate узнают текущий DNS endpoint;
- определить, что происходит при перезапуске плагина/Xray, смене порта и восстановлении интеграции;
- учесть, что текущая health-check конфигурация использует фиксированный HTTP health endpoint: отдельно решить, требуется ли автоматический выбор/публикация HTTP-порта или он остаётся независимым.

До согласования и тестирования этого механизма не считать DNS-порт автоматически выбранным и не фиксировать текущий порт как конечный контракт. Проработка должна быть совместима с ограничением: изменения только в репозитории плагина, без правок кода LucX-UI.

### D. Проверки и документационная приёмка

- README содержит приведённое TProxy-пояснение и последовательность DNS-интеграции.
- В PR нет изменений Xray routing rules, их порядка, Integrate/DeIntegrate или автоматического добавления DNS-правил.
- Нет утверждения, что текущий DNS-порт является окончательным.
- Есть отдельное техническое решение по выбору/резервированию/сохранению/объявлению DNS-порта и восстановлению после рестарта до завершения интеграционной реализации.


### E. Точная граница README: убрать противоречащие инструкции

В README оставить именно:
- обязательное TProxy-пояснение из раздела A;
- краткую схему прохождения DNS-запроса из раздела B.

Не превращать README в инструкцию по созданию/изменению Xray DNS outbound или routing rules, их порядку, Integrate/DeIntegrate либо автоматическому добавлению правил. Существующие подробные инструкции по добавлению DNS outbound/правил и проверке фиксированного порта должны быть пересмотрены и приведены к этой границе: никаких действий по изменению Xray-конфигурации в рамках этого этапа не описывать как необходимые изменения плагина. Упоминать порт 5355 (или другой текущий порт) можно только как временную текущую настройку/пример, не как контракт архитектуры.

README не должен утверждать, что автоматический DNS-port discovery уже реализован. До отдельного технического решения по его жизненному циклу это явно помечается как открытый вопрос разработки.
